# Game UI — board, modals, panels, zones

The largest UI subtree. Read first: `src/AGENTS.md`, `docs/STYLE_GUIDELINES.md`, `docs/agents/UI_THEME_RULES.md`.

## Layout

| Folder / file                             | Role                                                                                                                                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GameBoard.tsx`, `Game.tsx` (in `views/`) | Top-level board composition.                                                                                                                                                                                        |
| `panels/`                                 | Player inspection, mana pool, action log, and board controls. The spell stack is rendered by Pixi (`@/pixi/stack/StackLayer`), not React — only the `SpellStackModal` ("View") + `StackSection` summary stay React. |
| `zones/`                                  | Small React overlays — `LibraryZoneTile`, `ManaAbilityTapButton`, `HandCardActions`. The battlefield and hand themselves are rendered by Pixi (`@/pixi/BoardCanvas`), not React.                                    |
| `modals/`                                 | Non-engine dialogs such as target pickers, zone viewers, settings, and confirmation sheets. All built on the `Modal` compound.                                                                                      |
| `@/pixi/prompts/`                         | Native Pixi engine prompts, action cluster, game-over surface, keyboard handling, drag interactions, and dice feedback.                                                                                             |
| `game.types.ts`                           | Shared TS interfaces for board UI.                                                                                                                                                                                  |
| `game.constants.ts`                       | Magic numbers, phase definitions, sizing values, color arrays.                                                                                                                                                      |
| `game.styles.ts`                          | Reusable Tailwind class-string constants.                                                                                                                                                                           |
| `game.utils.ts`                           | Pure utilities (no React).                                                                                                                                                                                          |

When adding a constant, type, util, or class string, **check the shared modules first.** Don't duplicate.

## Board canvas — single unified Pixi scene

The whole table renders on **one** Pixi canvas, not one canvas per player. `BoardCanvas` (`@/pixi/BoardCanvas`) drives a single `BoardScene` (`@/pixi/board/BoardScene`) that hosts one `BoardRegion` per player, positioned by `computeBoardLayout` (`@/pixi/board/boardLayout`). Because every player's battlefield shares one coordinate space, cards can animate across the center line (MTGA-style combat staging) without crossing a canvas boundary.

- **Regions** (`BoardRegion`) own per-player grid layout, attachment stacking, rings, combat staging, and animation. The local region gets full interaction (drag/marquee/overlay); opponent regions are tap-to-target + hover only. Each reaches orchestrator services through a `RegionHost`. Combat attack rows always use the theme's hostile `promptAction.attackAction` colour; player colours remain limited to attacker identity marks.
- **Local controllers** live on the scene: `HandController`, `SelectionController`, `BattlefieldOverlay`, plus the `DragHandler` gesture. They talk to the scene through the `HandHost` / `SelectionHost` / `OverlayHost` seams in `@/pixi/board/types`.
- **Arrows + the spell stack + engine prompts** are not drawn inside `BoardScene`. A single transparent overlay canvas, `BoardOverlayCanvas` (`@/pixi/BoardOverlayCanvas`), sits _above_ the React panels and hosts `ArrowLayer`, `StackLayer` (`@/pixi/stack/`), `PromptLayer`, and `RulesCardPreviewLayer`. Its scheduler samples `BoardScene.getArrowDefs()` while arrows, image loads, stack tweens, previews, or animated prompts are active, then sleeps. `PromptLayer` renders the action cluster, every modal engine prompt, game over, and dice feedback. The canvas is `pointer-events: none` except while the cursor or a routed touch is over actual stack, prompt, or preview content, using each layer's `hitTest` rather than broad bounding rectangles, so interactions elsewhere pass through to the board. The stack layer registers itself with `BoardScene.setStackAnchorProvider`; the prompt layer's action bounds feed `BoardScene.setPlayerBlockers`.
- **`BoardCanvas` callback proxy is explicit.** Every callback added to `GameCanvasCallbacks` must also be forwarded through the object passed to `new BoardScene`; adding it only to the type and React producer silently drops the event at the canvas boundary.
- **React-driven Pixi setters must stay callback-free.** `BoardCanvas` applies `zoneTiles` from a React effect, so `BoardZoneTiles.setSpecs` must not re-emit hover callbacks for an already-hovered tile; callback-driven React state would recreate the specs and form an infinite render loop. Hover callbacks belong to pointer transitions.
- **Expanded action panel owns the top live-game layer.** `RightActionPanel` uses `z-[9001]`, one level above the live `BoardOverlayCanvas` wrapper at `z-[9000]`, so Log, Snapshots, and Dev cover the action prompt instead of the prompt bleeding through the panel. Portaled modal previews remain above both.
- **Layout** keeps the local player along the bottom. The default **focused** layout gives opponents fixed, overlapping play rectangles across the top; moving delimiter masks reveal one field without re-gridding its cards. Optional **overview** assigns opponents full-width horizontal bands and fits each grid to its actual band height. Compact screens retain focused layout. Each playmat fills its complete region to the viewport edges; only the center phase strip and explicit hand, HUD, and combat reservations reduce card placement space. `computeBoardLayout` owns these rectangles; `BoardCanvas` uses `scaleForRowsWithCombatRow` to fit cards without overflowing shallow bands.
- **Delimiters live in `BoardScene`.** In focused layout, `delimCurrent`/`delimTarget` partition the canvas into non-overlapping clip bands. Combat participants take precedence over manual focus, then hover, then active turn. Targeting, combat selection, hand drag, and inspection lock hover-driven refocusing. Overview bypasses delimiter easing. Reduced motion snaps delimiter changes.
- **Touch input.** All gestures are pointer-event driven. `LongPressGesture` (`@/pixi/LongPressGesture.ts`) implements the app-wide **long-press = preview** convention on Pixi surfaces (battlefield sprites via `BoardScene`, zone tiles via `BoardZoneTiles`, stack cards via `StackCardSprite`); the release-tap is swallowed (`consumeTap`) so a hold never triggers the tap action. Every hand card enters `useHandDrag` (document-level `pointermove`/`pointerup`/`pointercancel`, filtered by `pointerId`): release over the hand lets `HandController` commit its Pixi insertion slot, release over the battlefield casts only when the card has a direct cast action, and touch hold tears the drag down for the sticky preview. `useHandOrder` owns the client-only stable ID order; the cog-opened `GameSettingsModal` changes the persisted Manual/Color/Mana value mode without touching engine snapshots. DOM chrome (ZoneViewer, SpellStackModal, ActionLog, CardImageThumbnail) uses `useLongPressPreview`.
- **Hover detection** is owned by `BoardScene`. Focused layout checks the cursor against delimiter bands; overview checks both coordinates against the opponent's rectangle. Region highlights use the player's seat color and report `onHoverOpponent`. Hand exit detection also reconciles against document-level pointer movement because overlay ownership can suppress Pixi stage moves. DOM hand-action hover holds must release when their conditional panel unmounts.
- **Keyboard and screen-reader semantics stay React-owned.** `GameBoardAccessibility` mirrors players, hand and battlefield cards, direct mana actions, stack objects, zones, and phase stops as native controls while the Pixi canvases remain visual/pointer surfaces. Global `useKeybindings` preserves native Enter, Space, and navigation-key behavior when focus is on a control.
- **Pixi player HUD + on-grid zones**: the player panel is **all Pixi, always on** — there are no React player panels (the old `PlayerPanel`/`PlayerAvatar`/`BadgeOrbit`/`ZoneActionColumn` chain and the `pixiPlayerBar` pref were removed). It lives in `@/pixi/hud/`:
- **`PlayerHudLayer`** owns one **`PlayerHudCapsule`** player plate per seat and a shared tooltip. Desktop horizontal plates use a fixed 58px row showing avatar, life, hand count, and compact state icons. The game menu's settings cog lives in the desktop action-cluster header, not on the player plate. The entire player plate uses a pointer cursor and opens `PlayerSheetModal`; while the player is a legal target, the same full hit area targets them instead. Targetability and selection highlight only the avatar border, never the panel bounds. Player names and textual turn/priority labels do not render on the plate. Life sits immediately right of the avatar, then hand count; the vertical divider renders only when a state icon follows it. Player plates have no background surface, perimeter, or seat-color rail; only their controls and state marks draw chrome. Mana floats on its own compact tray above or below the plate rather than stretching the player plate.
- **Collapsed opponent panels** render only live resources: the mana tray is absent when every mana value is zero, and the status tray is absent when no player-status badges exist. They do not render a Details/overflow control because the whole player plate opens `PlayerSheetModal`.
- **`BoardZoneTiles`** renders library, graveyard, exile, and command on reserved grid cells. Library, graveyard, and exile default to successive rows in the first available column; each region persists its selected fallback cells across relayouts, and explicit local drags update those same slots. Library keeps its offset pile silhouette with dark separators, while the Scryfall card-back JPEG is clipped to the shared card radius because its source pixels are near-white outside the printed rounded corners. Nonempty public zones show their top card and count. Empty graveyard and exile zones retain dotted card-slot outlines around their subdued glyphs and labels; all empty zones keep bounded hit areas. Clickable tiles fade in the shared `cardRing` glow with GSAP on pointer hover. Empty-tile ambience uses additively blended Pixi `Graphics` advanced by the existing `BoardRegion.animate` tick: library page wisps rise, graveyard ash settles, exile motes orbit a void ellipse, and command sparks circle a seat-coloured sigil. Any tile showing a card replaces particles with a layered magical glow pulse beneath the card perimeter. Hovering a populated command tile opens every command card in one pointer-traversable overlay group. That group follows the global in-game printed/rules preview preference and keeps the shared preview machine's tile-to-preview hover grace. Ambient effects mutate transforms and alpha only and disappear when animations or reduced motion disable motion. An opponent tile in the synthetic attack-row slot uses the stable full-field playmat rect so its complete card footprint remains inside the playmat border as delimiter bands resize. Opponent tiles remain non-draggable. `BoardCanvas.zoneTiles` is the only zone state bridge into Pixi.
- **Keep-outs** use the local player's rendered plate, each focused opponent field's stable expanded-plate footprint, the native Pixi action cluster, and the visible hand strip. Opponent delimiter hover changes only clipping; it never changes grid blockers or repositions battlefield cards and zone tiles. Floating mana overlays the battlefield without triggering a re-grid. `HandController.getBlockerRect` is root-local and independent of current hover/drag. Grid reserve and hand blockers use the same desktop/compact trim; the action cluster receives the full visible height. Grid debugging draws legal card slots and blocker rectangles separately; it does not render blocked cells as card-shaped placement options.
- **Mobile-minimal mode** (`useIsMobileGame` = short screen AND coarse pointer; desktop is byte-identical when it's false):
  - **Phase strip** (`@/pixi/PhaseStripLayer`): desktop reserves a 30px center band with 1px of vertical padding around its 28px cells. Compact renders the current phase as a tappable pill. Expanding it reveals the full stop controls without reflowing the board; outside tap or idle collapses it. Desktop keeps the full phase sequence and combat substeps. Controls sit between the separated playmats on a seat-colored center divider that identifies the active turn, without a backing band. The active phase uses the bordered cell treatment rather than a second underline. Player plates do not repeat priority. The strip stays readable during combat.
  - **Action cluster** (`@/pixi/prompts/PromptLayer`): native Pixi buttons use explicit hit areas, pointer states, accessibility metadata, and semantic `promptAction` colours. Desktop includes the mode and board-menu controls. Compact removes the header, anchors the cluster vertically around `dividerY`, and hides it while the board is dimmed. `PromptLayer.getActionBounds()` reserves the rendered rectangle from battlefield layout.
  - **Hand fan** rests partly below the canvas edge, sinking further in compact mode (`HAND_BOTTOM_SINK_FRAC_COMPACT` versus `HAND_BOTTOM_SINK_FRAC`). Hover lifts and enlarges the card while pushing neighboring cards aside. Opening hands use the same fan and mulligan controls as normal play, without a separate raised presentation or veil. Whole-table pinch zoom retains its existing behavior.
  - **Player plates** retain readable life and hand counts instead of scaling the whole HUD down. Narrow opponent bands use a vertical layout; shallow horizontal plates keep life beside the portrait whenever their height can contain it, while extremely short plates omit the portrait. Opponent plates align inside the playmat's top-left corner. The local plate aligns inside the bottom-left corner, narrows toward the hand when enough usable width remains, and moves above the hand only when necessary to prevent overlap.
  - **Zones move onto the player plate** in compact mode, except command stays on-grid. Expanded plates show zone state beside hand count; tapping any part of the plate opens full player inspection, where zone actions remain live. Command tiles show the snapshot's optional `commanderTax`; never derive it from mana cost or local cast history.
  - **Row fitting** uses the exact shared solver, including the edge-to-edge playmat, trimmed hand reserve, and combat band. Compact targets three rows; overview caps opponent grids at one row plus their combat band. The hand reserve derives from its visible fraction and `HAND_RESERVE_TRIM` / `HAND_RESERVE_TRIM_COMPACT`.
  - **Battlefield long-press** opens the **sticky** card preview (with the existing flip/rotate buttons and outside-tap dismiss): `BoardScene.fireLongPressPreview` → `GameCanvasCallbacks.onLongPressCard` → `Game.tsx` `preview.showSticky`. `CardPreview` clamps its size to the viewport height in compact mode.
  - **Player plate tap = inspection.** Every player plate uses one full-panel hit area and opens `PlayerSheetModal` unless that player is currently targetable, in which case the same hit area submits the target.
  - **ManaAbilityTapButton** long-press shows a transient description popover (the hover `title` equivalent).
  - **Card-relative chrome** scales with the sprite. Compact sprites/tiles get a touch hit-pad from the free cell pitch, and rings remain at least two screen pixels. Battlefield action overlays expose tap, untap, waterbend, selection, and available mana choices; ordinary taps inspect only when no direct action is available.
  - **Battlefield lab**: `GameDevPanel`'s Player workspace can force every identity, turn, targeting, combat, connection, badge, counter, life, hand, incoming-damage, and W/U/B/R/G/C mana-pool state across every seat. Its Board workspace can reveal each transparent player panel's complete layout box. Its Prompt workspace can force every action-cluster state and open every prompt modal, battlefield dialog, and game-over screen with representative data without sending engine responses. Every workspace has its own retained search query that filters its controls. `BoardPlayground` also has a four-player `player-panels` scenario with simultaneous states, partner commander damage, and independently editable floating mana. Turn/priority changes leave those fixtures intact. Its overflow opens the same live player detail sheet as the game. The right action panel's Dev tab and `Command+Shift+D` toggle are enabled only when `import.meta.env.DEV` is true.
  - **Native tap feel** is global CSS, not mobile-gated: `index.css` sets `-webkit-tap-highlight-color: transparent` on body, `touch-action: manipulation` on tappable elements, and the `.game-touch-surface` class (on the `Game.tsx` root and the `Modal` backdrop — modals portal to `document.body`, outside the game root) suppresses text selection, iOS image callout, and image drag ghosts; inputs keep text selection.

The legacy per-player canvases (`PixiGameCanvas` / `PixiGameScene` / `PixiArrowsCanvas` / `PixiPhaseStripCanvas` / `OpponentHalf`) have been removed — do not reintroduce them.

## Game loading

`GameLoadingScreen` keeps setup progress centered and presents `GameLoadingTip` as the progress card's attached footer so setup status and rotating guidance read as one surface. Configure copy, audience, keybinding IDs, cadence, and transition duration in `gameLoadingTips.ts`; keybinding tips render the player's persisted shortcuts, while touch loading screens exclude desktop-only entries.

`useGamePrefetch` blocks board reveal only on immediately visible printed-card textures. It warms the complete deck pool's printed textures in the background, then lazily warms the same pool's `art_crop` textures without extending the loading screen.

## Modal pattern

All game modals use the `Modal` compound:

```tsx
<Modal onClose={onCancel} maxWidth="max-w-md">
  <Modal.Header>{/* title + optional source-card thumbnail */}</Modal.Header>
  <Modal.Instructions>Instruction text</Modal.Instructions>
  <Modal.Body>{/* content */}</Modal.Body>
  <Modal.Footer>{/* buttons */}</Modal.Footer>
</Modal>
```

Use `Modal.Close` for buttons and `Modal.CloseShortcut` for remappable keybindings that dismiss a dialog so both paths finish the exit transition before unmounting. `Modal` owns the nested-dialog stack, focus containment, topmost Escape handling, backdrop dismissal, and reduced-motion-aware entry and exit transitions.

Card browsers use `DialogCardBrowser`. It keeps search, collapsed type and color filters, sorting, scroll position, keyboard navigation, and per-card view state together. Zone viewers render cards in a virtualized grid through `DialogCardPickerScene`, using the same 1160px panel maximum, 16px viewport-height margin, effective 28px card inset, `fitPromptCardDimensions`, orientation-aware scale, `PROMPT_CARD_GAP`, and `PROMPT_CARD_ROW_GAP` as `chooseCards` and `revealCards`. Do not add captions beneath picker cards because they change the shared row pitch; card names remain available through the card face and accessible option label. Landscape cards retain the portrait scale instead of fitting their long edge into a portrait slot. Keep every card at full opacity and activate legal direct actions without an extra tray confirmation; manual moves retain the explicit footer action. Hover and keyboard focus use the shared `gameTheme.cardRing` hue, with clicked or selected cards allowed to strengthen that ring without recoloring it. After changing a picker card's scale, call `syncHandControlsScale`; otherwise its view and face controls inherit the card scale until a face toggle reflows them. Keep `CARD_BROWSER_HORIZONTAL_PADDING` and `CARD_BROWSER_VERTICAL_PADDING` in `cardBrowser.ts`; the React accessibility controls and Pixi scene must use the same cell geometry.

## Mana text

React text that may contain `{W}`, `{2}{R}`, etc. renders through `DynamicTextRender`:

```tsx
<DynamicTextRender className="align-middle" text={description} />
```

Pixi text uses `PixiRichText` so it shares the mana-symbol cache and wrapping behavior. Reuse these renderers instead of parsing symbols in each caller.

## Sizing

`GAME_CARD_SIZES` in `game.constants.ts` is the single source of truth. Use one of its three base dimensions and scale responsively when the viewport requires it.

| Size          | Dimensions  | Usage                                                                                                       |
| ------------- | ----------- | ----------------------------------------------------------------------------------------------------------- |
| `battlefield` | `70 × 98`   | Battlefield cards and zone tiles; battlefield preferences and grid fitting may scale this base size         |
| `hand`        | `130 × 182` | Hand cards and non-actionable zone browser cards; `useHandScale` may scale this base size                   |
| `preview`     | `300 × 420` | Prompt choices and sources, actionable zone pickers, stack cards, command-zone previews, and hover previews |

Preview cards may shrink to fit the viewport. Landscape cards use the same uniform scale as portrait cards, swapping the shared dimensions from `300 × 420` to `420 × 300`; never fit a landscape long edge into the portrait short-edge slot. Keep `RulesCardPreviewLayer` as the shared rules renderer and do not add context-specific preview dimensions.

## Card rendering ownership

Four renderers draw cards. `components/game/cardPresentation.ts` provides shared data for type lines, counters, state, costs, progression, and stats. Each renderer draws that data itself. `HandRulesCardFace.ts` is an adapter, not a fifth renderer.

| Renderer                                      | Tech | Where it shows                                                                                                   |
| --------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------- |
| `@/pixi/CardSprite`                           | PIXI | In-game battlefield + hand (the real game)                                                                       |
| `components/game/BattlefieldCardFace`         | DOM  | Custom battlefield styles (art-forward / mini-frame), settings preview, and dev gallery (`/card-mock`)           |
| `components/game/CardPreview`                 | DOM  | Printed-card hover preview in-game and across deck/editor surfaces                                               |
| `@/pixi/cardPreview/RulesCardPreviewLayer.ts` | PIXI | Every rules card: board hover plus embedded hand, prompt, and stack views through `HandRulesCardFace.ts` adapter |

**Rule:** when you add, restyle, or remove a card visual — counters, damage wash, summoning-sickness, P/T coloring, frame tint/bars, keyword chips, mana pips, foil, badges, etc. — change **every** renderer that should show it, in the same commit. A change that lands in only one drifts the others (this has bitten us repeatedly: FPS-style regressions, counter display, damage-wash corners, summoning sickness).

- **Shared, theme-driven color math lives in `@/themes/gameTheme.ts`** (`frameTint`, `readableTextColor`, `withAlpha`, `darken`, `relativeLuminance`). Use these in both DOM and Pixi instead of re-deriving — that's what actually keeps the look identical across renderers. No hex literals (see Theme below).
- **Geometry must match too.** A full-card overlay must trace the card's rounded corner: in the DOM the card border is drawn as an `inset-0 rounded-[inherit]` overlay (not a CSS `border`) so washes can fill to the outer radius; in Pixi the equivalent is a `roundRect(..., CARD_RADIUS)`.
- **Use `PtBadge` for realistic P/T badges.** `Card` and `CardPreview` place it at the bottom right. Size it with container units (`cqw`) and `em` so stacks, modals, zones, and hover previews keep the same proportions. The card root must set `@container`. Do not add another pixel-sized P/T span. Printed hand faces already include P/T in the image; `HandRulesCardFace` puts the live value in its footer. Every battlefield style calls `CardSprite.updatePT`. The card DTO must retain `types`, effective `power` and `toughness`, and printed `basePower` and `baseToughness` so each renderer can derive the same P/T color.
- **Attacking + summoning-sickness now match the DOM in Pixi too:** both draw an inset **edge glow** (`CardSprite.updateEdgeGlow`) — red for attacking, frosty + pulsing for summoning-sick (pulse driven per-frame by `BoardRegion.animate` → `tickEffects`); summoning-sick also keeps the grey desaturate/dim filter. Pixi's `setRing` is now reserved for **interaction/combat** states only (lethal, pending, tappable/untappable land, selectable/targeting).
- **Known intentional divergences — do not "fix" without being asked:** some effects are **Pixi-only** (doomed wash, foil ring, ring-bearer, status badges `MORPH`/`EXERTED`/…, damage-order badge, stack count). The DOM face also currently lacks the _debuffed_ P/T color that Pixi has.

## Card preview (hover / sticky)

The app has one preview state machine. Games can use the persisted printed-card renderer or the Pixi rules renderer. Deck, editor, limited, and modal views always use the DOM renderer.

The rules-backed option is labeled **Rules** because it represents current game state, not only Oracle text. Keep **Hand default view**, **Stack default view**, **Prompt and dialog default view**, and **Board hover preview view** adjacent in Board settings.

In-game preview triggers are **Hover** and **Right click** only. Right click passes the same source-card rectangle and uses the same anchor gap as hover; stickiness changes dismissal, not placement. Persisted modifier-trigger values normalize to Hover. Realistic and Rules placement share `CARD_PREVIEW_ANCHOR_GAP` and `CARD_PREVIEW_EDGE_PAD`, so switching with `R` does not move the card.

| Layer         | File                                                                                                                      | Role                                                                                                                                                                                                                                                                                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Machine       | `lib/cardPreview.ts` (`CardPreviewMachine`)                                                                               | Stores preview state and controls every timer. `PREVIEW_TIMING` contains the warm and cold show delays, leave grace, enter and exit timing, and battlefield hover-out hold. The cold delay comes from the user's Card Preview Delay preference.                                                                                                                      |
| Hook          | `hooks/useCardPreview.ts`                                                                                                 | React binding built on `useSyncExternalStore` and stable callbacks. Callers opt into the in-game trigger preference with `useTriggerPreference`; delayed callers use the persisted hover delay.                                                                                                                                                                      |
| DOM renderer  | `components/game/HoverCardPreview` → `CardPreview` (+ `CardPreviewOverlay`, `CardPreviewActions`, `cardPreviewLayout.ts`) | Draws printed cards. `computePreviewLayout` calculates placement. `CardPreviewRail` controls its portal slot, collapse state, resizing, and optional caller details.                                                                                                                                                                                                 |
| Pixi renderer | `pixi/BoardOverlayCanvas` → `pixi/cardPreview/RulesCardPreviewLayer.ts` (+ `PixiCardRailPreview.ts`)                      | Draws every in-game rules card. `HandRulesCardFace.ts` embeds the same renderer inside hand, prompt, and stack `CardSprite`s. The overlay routes preview and stack hits, dims and blocks the battlefield behind sticky actionable previews, dismisses outside taps, handles keyboard actions, and scrolls on touch. The rail reads the shared `cardRailState` model. |

`rulesCardPreviewPresentation.ts` chooses the displayed face independently of live game state. `RulesPreviewActions.ts` renders current-face actions, including Class level-up, in a collapsible section separate from Oracle text. In the field preview, available actions precede supplemental details. Status chips support every DOM-preview tone and use a solid status fill with uppercase `textOnTinted` labels. Do not infer actionability from text similarity because Oracle text lacks stable engine ability IDs. Inactive faces use printed metadata and label current-face actions separately. Faceless cards expose neither identity nor Oracle text.

`Game.tsx` resolves the hovered ID against visible and stack cards, falling back to the prompt-provided card for card-browser modals, and opts its board preview machine into the in-game trigger preference. `StackObjectDto.text` is producer-owned stack text, not Oracle text: Forge sends `getStackDescription()`, while the Rust producer currently sends the stored `ability_text`. Stack card stubs therefore leave `CardDto.text` empty; `RulesCardPreviewLayer` derives their printed presentation immediately from the matching `DeckCard` through `deckCardToPreviewDto`, then uses Scryfall metadata for missing or face-specific data. Matching `DeckCard` records supply stored image URIs and deck metadata, while `useScryfallStore` owns card-face metadata lookup, texture loading, request deduplication, and caching. Live renderers must request card-face metadata and textures through `useScryfallStore`; never call the Scryfall API or load Scryfall card images directly. Start texture loading immediately from the matching `DeckCard`; do not gate its stored image URI on the asynchronous metadata lookup. Do not cap the shared texture map by forgetting live textures: preview and board sprites still own those textures, so forgetting them saves no GPU memory and forces duplicate network fetches and image decodes. When a stack identity's exact set and collector lookup fails, rules metadata falls back by card name while artwork remains tied to the stored printing URI. `StackObjectDto.sourceAbilityText` is the canonical human-facing source ability represented by that entry; non-permanent entries fall back to `text` only when a producer omits it. The inline stack rules face normalizes that text against individual Oracle lines and repeats no line already shown in the body. Keep producer text separate from printed fallback data.

`RulesCardPreviewLayer.ts` is the sole Pixi rules-card renderer. It owns identity, artwork, available actions, progression rails, supplemental details, Oracle text, flavor, collapse state, scrolling, and stack-effect highlighting. `HandRulesCardFace.ts` is only an adapter that embeds that renderer inside hand, prompt, and stack `CardSprite`s; it must not implement a second presentation path. Context-specific code may control placement, scaling, face selection, outer controls, and the highlighted stack effect only. Keep each rules preview in its own Pixi render group: the overlay can show several stack and prompt cards at once, and merging their frequently rebuilt Graphics/Text instruction streams causes missing texture batches.

`BoardRegion`, `HandController`, `BoardZoneTiles`, `StackLayer`, `RulesCardPreviewLayer`, `DialogCardCanvas`, and `DialogCardPickerScene` bind their sprites directly. There is intentionally no app-wide sprite registry.

`deckCardToPreviewDto` is the boundary from persisted `DeckCard` data to preview renderers. It must overlay `GAME_CARD_DEFAULTS` and normalize every required `CardDto` collection and scalar; old deck records and `DeckCard` itself do not carry live-game fields such as attachments, choices, progression arrays, or status flags. Never restore the direct type assertion because rules and printed preview presentation read those fields synchronously.

Supplemental costs omit only exact normalized Oracle entries, not incidental mentions of an ability. Show every unique engine keyword even when Oracle text repeats it because the collapsed section is the keyword index. Keep Oracle lines in source order and draw each supplemental keyword as a separate chip. Split at the first colon. Render a recognized mana suffix as symbols; discard an engine payload such as `Copy:DBCopy:Optional` instead of showing it. `pixi/cardPreview/previewScroll.ts` cancels native wheel and touch scrolling over every rules preview, including embedded hand and stack cards and scroll boundaries. Pixi propagation cannot prevent page scrolling. Bind native scrolling through the canvas that owns the rules card; overlay-only routing cannot reach hand cards on `BoardCanvas`. Leave wheel events outside the preview and Ctrl+wheel unchanged. A stack card in rules view stops pointer down and tap propagation before the stack card's open and long-press handlers; section controls own those interactions. Set `RulesPreviewActions` to `embedded` when it lives inside the external preview card body so the outer scroller remains the only scroll owner. Inline hand previews also set `ownsScroll` because their clipped actions panel scrolls independently.

Rules and printed previews choose portrait or landscape geometry per displayed face. Every face keeps its native orientation: hovered horizontal hand cards open landscape, and flipping a Battle changes its landscape front to the portrait back. `F` flips eligible double-faced cards; horizontal single-face and multipart cards do not rotate to portrait. Split, Room, aftermath, adventure, and flip-card sections share `resolveCardFaces`; cards sharing one image are multipart, not flippable.

`rulesPreviewFrame.ts` draws neutral `appTheme` surfaces and flat name and type bands. Avoid per-card decorative tessellation here: stack and prompt overlays can render several rules cards in one frame. Card colors and types do not tint the frame. `cardPreviewStyles.ts` owns the actionable-card glow used by both the printed preview and the DOM glow that `BoardOverlayCanvas` synchronizes to the Pixi rules card; keep the effect shared instead of drawing another Pixi approximation. `RulesPreviewSectionHeader.ts` controls artwork, available actions, rules, progression, supplemental details, and flavor collapse state.

`previewHoverArea.ts` defines curved transfer areas from the source card to the preview and between the preview and its controls. Cover diagonal departures above and below the source, not only the gap between facing edges. `BoardOverlayCanvas` derives enter and leave callbacks from pointer position so crossing a gap cancels dismissal immediately. Returning to the source keeps the preview open without intercepting the card. Use these curves only for hover; wheel routing and sticky-touch dismissal use visible panel bounds.

Protect hover as soon as the preview opens. Use final layout coordinates rather than animated transforms. Do not wait for click readiness: its 300 ms entry delay exceeds the 120 ms leave grace. `onInteractionReady` rechecks the last pointer position so a stationary pointer becomes interactive without another move.

Pixi's `EventSystem` hit-tests document-level pointer moves in every canvas, even when another canvas is the DOM target. CSS pointer ownership does not block board-card hits. `BoardOverlayCanvas` registers `BoardScene.setOverlayHitTest` in shared canvas coordinates. The board stage rejects preview, bridge, prompt, and stack hits before dispatching to hand or battlefield children, and overlay pointer-downs suppress the same pointer's board tap so a retained zone press cannot activate during an overlay state transition. Stage leave clears hand hover. Active board and hand drags bypass this rejection. Remove the provider when the overlay unmounts or the scene is replaced.

`TargetingCursor` listens for pointer movement in the capture phase so modal event isolation cannot hide the target cursor while it passes over zone viewers. Keep its listener native and capture-based.

Keep landscape artwork above the rules. `RulesPreviewArtwork` owns single-face fitting for field previews and the inline hand, stack, and prompt rules faces: portrait layouts use top-aligned cover with the theme-paper fade beginning at 85%, while landscape layouts use contain. Portrait cover artwork overlaps the title band by one design pixel while preserving its bottom edge. The transparent fade and multipart artwork mask use one top-square, bottom-rounded path; composing a rounded rectangle with an overlapping top rectangle creates a raster seam one corner radius below the artwork edge. Portrait overflow is cropped through a texture view, and the fade and corner cover draw without stencil masks; do not reintroduce artwork masks, because prompt drag origin transforms leave masked artwork anchored behind the moving card. Split and Room halves align their name, mana, artwork, type, and rules columns. `RulesPreviewIdentity.ts` draws the identity text. Artwork halves are texture views over one cached source and use contain fitting. Destroy the views, never the shared source. Both rules columns share one scroll position. Do not move horizontal artwork into tall sidebars.

Mana headers use the canonical Pixi `parseManaCost` parser. Forge's `no cost` sentinel renders empty, while an actual zero mana cost retains its symbol.

Forge spells the live defense counter `Defense`. Missing loyalty or defense counters mean zero on the battlefield, not the printed starting value.

The in-game lab's Card tab and `/card-mock` share `components/dev/devPreviewScenarios.ts`. The playground opens a scenario directly and supplies local action controls and viewport sizes. Scryfall can report Room and aftermath cards as `split`, and Battles as `transform`; use the shared layout and type predicates instead of relying on one layout string per mechanic.

Rules that preserve fixed behavior:

- **Never unmount the preview on transient state.** Engine prompt churn (a prompt answered and replaced within a frame) must not blink the DOM: pass `suppressed` to `HoverCardPreview` (opacity fade; hover state survives) instead of adding conditions to the mount gate. Unmount-gating on `promptType` is exactly what caused the show/hide/show flash.
- **Explicit UI takeovers dismiss.** Zone viewer, spell stack modal, ability picker, hand drag: dismiss via the hook's `dismissDeps` argument or `dismiss()` (synchronous — never `setTimeout(dismiss)`).
- **Instant card-switching is only allowed while `open`.** A dismissed preview re-enters through the hover delay; the machine enforces this so a pointermove racing a dismiss can't re-show it for a frame.
- **`phase === "closing"`** keeps the card rendered for the exit animation (`PREVIEW_TIMING.exitMs`); `hoveredCard` is non-null during it.
- **The machine is warm for `warmWindowMs` after a preview was visible**: hovers during that window show at `warmShowDelayMs` instead of the preference delay, so browsing a board feels fluid without making the first popup twitchy.
- **Enter/exit is a hero zoom from the hovered card's rect**: `CardPreview` feeds `--preview-shift-x/y` + `--preview-scale-from` (computed from `anchorRect` vs the final position) into the `preview-in`/`preview-out` keyframes in `index.css`. Keep the animation anchored — an in-place zoom reads as a blink.
- **The preview is pointer-transparent until the enter lands** (`entered`, timer-armed — not `animationend`, which never fires under `prefers-reduced-motion`). The hero zoom travels across the hovered sprite; an interactive preview crossing the cursor steals pointer events from the canvas and kills the sprite's hover state.
- **Card face chrome matches Pixi geometry**: corner radius is proportional (`CARD_RADIUS / CARD_W` of card size — shared constants in `game.constants.ts`). Printed previews use the card image's own border; color-identity border chrome is reserved for the rules view. Don't reintroduce fixed `rounded-*` on the preview card.
- **Images are monotonic** (`PreviewImageStack` in `CardPreview`): pixels already shown are never removed until the replacement loads. Swapping an `<img>` src blanks it instantly — a naive URL swap (Scryfall faces resolving, low→high res, card switch) is the image flash.
- **Battlefield hover-out is `BoardScene`'s** (`scheduleHoverClear`, also fired on sprite `destroyed` — a removed sprite emits no `pointerleave`). Hover is also **re-asserted on every `pointermove` over any sprite** (force `setBattlefieldCardHovered` — not just the remembered card): a spurious `hoverEnd` (the preview firing enter/leave as it jumps positions during an instant switch) must not close a preview while the cursor sits on the card, and a `pointerenter` swallowed whole by the hand-hover gate (`hasActiveHover`, e.g. the fan grazed mid-sweep) leaves the scene with a stale hover belief that only raw pointer truth can repair — gating the re-assert on `hoveredCardId` is exactly what made a preview die permanently on the card you stopped on. The machine keeps the re-assert free — `hoverStart` early-returns when the same card **object** is already open, and a changed DTO object refreshes the open preview.
- **Zone changes follow authoritative snapshots.** Battlefield entries removed by a snapshot fade in place; the client does not synthesize flights toward destination zones. Seed positions and scales for battlefield arrivals and cross-region combat movement are canvas-global, converted through the root transform at region boundaries.

## Prompt routing

The engine sends a `Prompt` (from `@/protocol`) → `Game.tsx` builds a `PromptOverlaySpec` → `BoardOverlayCanvas` forwards it to the public `@/pixi/prompts/PromptLayer` orchestrator. `PromptLayer` owns lifecycle, keyboard handling, and the action cluster; `PromptModalLayer` renders modal and game-over surfaces; `PromptLayerBase` owns shared prompt/card/drag state and drawing primitives. The hierarchy switches on `prompt.input.type` and answers through `respond(<PromptOutput>)`. Modal prompts own the full overlay hit area; the action cluster reports only its rendered bounds. Non-prompt overlays such as zone viewer, spell stack, and ability picker remain React in `GameOverlays`.

Engine modals, including damage order, can minimize and reopen without clearing their pending choices. A collapsed damage-order prompt routes to `promptRequired`, not `noAction`, so its reopen control remains available. Reopening a modal prompt atomically closes any zone viewer; these are competing inspection surfaces, and retaining the zone lets the restore pointer reveal or reactivate it.

Card-bearing prompts use hand-style cards inline. `chooseCards`, `revealCards`, `reorder`, and `scry` all build those cards through `PromptModalLayer.createCardTile`; selection and drag/drop stay on the tile, not the rules face. Prompt cards use `GAME_CARD_SIZES.preview` and shrink against the viewport height so a Scry pool, destination row, and footer fit without scrolling at standard desktop sizes. New prompts use the persisted **Prompt default preview** preference and default to the realistic face. Hover or focus a prompt card before using the configured change-view and flip-face shortcuts. A card with an available selection, activation, or drag action gets the same thin interaction ring as battlefield sprites; source cards, reveal-only cards, and unavailable cards instead enlarge slightly without a glow. Background hand-card shortcuts must yield while one of these card modals is open so the prompt card owns those bindings.

Choose/reveal card prompts size to their card content, using the text-choice width for small or empty sets and the shared card-modal cap for larger grids. Apply viewport and source-rail constraints before calculating columns; unused panel width must not push the source card away from sparse choices.

Prompt tiles and source previews reuse `HandCardControls` for printed/rules view changes and eligible face flips or landscape rotation. Controls and keyboard shortcuts share per-card state. Control presses stop before tile selection or dragging; hovered cards rise above overlapping neighbors so their controls remain reachable, while dragged cards retain the higher drag layer.

Prompt card wrappers add feedback and selection/drag behavior without taking input from embedded rules controls. The rules body owns presses and touch scrolling; artwork remains available for outer card gestures. `PromptLayerBase` resolves rules scrolling from the actual Pixi hit target, so sources and tiles share one native scroll route through `BoardOverlayCanvas`, respecting masks and modal ownership. Card feedback, section hover/toggles, and scrolling request rendering through the existing callbacks rather than relying on another surface's ticker.

Every draggable prompt card lifts with a stronger `gameTheme.cardRing` outline and tilts slightly with horizontal pointer movement. Return scale, rotation, origin, and ring state during both successful and cancelled drag settlement; respect reduced-motion preferences.

Dice prompts use flat cached face and pip geometry with the player's color on the border. Arrange results in stable centered rows and start every displayed die together through short deterministic `@/pixi/effects/gsap` motion paths with per-die direction, distance, curvature, duration, and spin. Endpoints remain ordered even though the rolls vary; do not reintroduce shuffled placement, top-of-modal drops, particles, auras, glints, shadows, or decorative facets. Drive transient values from shared elapsed time and lock each result when its die lands. Reduced motion settles every die immediately.

Zone viewers always use the compact Pixi card grid; do not replace browse-only zones with the side inspector layout or autofocus the first card when the modal opens. Hover or keyboard focus slightly enlarges browse-only and unavailable cards without a glow; every hovered card remains eligible for the configured change-view shortcut regardless of action legality. Legal actionable cards instead receive the thin `gameTheme.cardRing` feedback without requiring a click first. Persistent selections use `gameTheme.cardSelection`. In actionable modes, legal playable or targetable cards use `CardSprite.setPlayableRing`, giving them the same thin, vibrant pulse as playable battlefield cards; hover and selection temporarily replace that pulse with their stronger static feedback. Embedded rules faces bind the shared preview-scroll routing to the zone canvas so wheel and touch scrolling stay inside the card instead of moving the browser grid or activating the card. Keep every card at full opacity so zone contents remain readable; unavailable and pending cards communicate through cursor, hover-scale, and ring behavior instead of fading. Browse and cast activations close the zone after dispatching the card action so play-mode or payment prompts receive the full surface; target and cost selection keep it open across repeated choices. Target, cast, browse-action, and cost modes activate legal cards directly; browse-only card clicks do nothing, and manual moves retain the explicit footer confirmation. Keep final card positions stable and reserve persistent checks for actual selection.

Scry drag targets highlight the full rounded zone border, including the source pool. Highlight graphics remain pointer-transparent and clear when the drag leaves or ends. The pool never compresses card spacing to fit: cards keep full `cardWidth + PROMPT_CARD_GAP` slots inside a masked, wheel-pannable window (thumb under the row) that appears only when the row overflows. The drop preview slot clamps into the visible window, dropping into the pool scrolls to the appended card, and the offset survives rebuilds (minimize/reopen, moves) but resets with the prompt.

Choice-search focus is independent of the query text. Show the themed focus border and a typing caret while focused, preserve focus across filter-result rebuilds, and use a steady caret under reduced motion.

Modal prompt wheel scrolling preserves pixel deltas, converts line/page deltas, scales the result, and clamps only extreme steps. Do not replace it with a fixed step per wheel event because trackpads emit many small events. Enter and Space activate the available primary footer action. A focused choice-search field keeps Space as text input instead.

`useKeybindings` capture listeners stop propagation only when a handler does not return `false`. The global `pass-priority` handler must return `false` when it has no action for the current prompt so Space reaches `PromptLayer`; swallowing that event breaks modal primary actions such as Reveal's Continue.

`reorder` keeps every card in one **Resolution order** strip whose height hugs the card row and its controls; size the modal to that strip plus its header and confirmation footer rather than the viewport. The leftmost card resolves first, and horizontal drop position chooses the insertion index. While dragging, close the source gap and glide neighboring cards aside to expose the pending destination before release; do not mutate the submitted order until drop. Initialize the strip from the engine-provided order, center the earlier/later controls beneath each card, and use `gameTheme.cardRing` for their hover/focus accent. After either a drag or button move, preserve each card's previous global position so displaced cards glide into their new slots without replaying a scale pulse. Inset both the strip and its cards far enough that rank badges, rings, and rounded borders remain inside the modal mask.

Center each prompt-and-source cluster on the viewport. Every prompt with a source card reserves the right-side rail beside the minimize control and uses `PromptLayerBase.promptSourceCardDimensions()`, capped by `GAME_CARD_SIZES.preview`, so source previews have one ruleset-defined size across prompt types. Shrink the modal before shrinking or moving the source; when the complete rail cannot fit, stack the same source preview inside the modal and let the body scroll. Live prompts use `currentPrompt.sourceCard` directly; fixtures may fall back to `sourceDeckCard`. Apply `currentPrompt.sourceAbilityText` through `CardSprite.setHandRulesHighlight` so the resolving rules entry receives the same pulse used by stack rules cards.

`PromptModalPreview` must portal `BoardOverlayCanvas` directly to `document.body`. `RightActionPanel` uses `backdrop-filter`, which creates a containing block for fixed descendants; an inline full-screen preview canvas is then constrained to the panel while retaining a viewport-sized Pixi coordinate system, leaving the prompt off-screen and capturing input.

Standalone prompt previews register their canvas host with `modalStack`: `scene={null}` bypasses the live overlay's `BoardScene.setOverlayHitTest` provider. Board and overlay stage hit tests must reject input beneath the top modal; the owning prompt canvas retains pointer and keyboard input. Document-level board hover reconciliation must also yield to the live overlay hit test.

The open Dev tab sits above the gameplay overlay but below portaled full-screen prompt previews. Touch routing must respect the topmost DOM element before replaying a touch onto the canvas. Scry's landscape, double-sided, and mixed-layout dev choices load real card metadata through the shared Scryfall store and reuse the preview scenario catalog.

## Theme

This subtree is the most color-heavy in the app. **No hex / rgba / palette tailwind.** Add a semantic key to `GameThemeColors` (in `src/themes/gameTheme.ts`), wire it in `buildGameColors()` (in `src/themes/buildGameColors.ts`), regenerate the Tailwind `@theme` block with `node scripts/generate-theme-css.mjs --write`, then use the generated token utility (`bg-targeting-hostile`, `text-counter-p1p1`, `ring-card-ring`, `bg-pt-buffed`, …). See `docs/agents/UI_THEME_RULES.md`.

Use `PromptButton.action` for gameplay buttons and `variant` for app actions so the corresponding foreground is applied. Pass and priority actions use the app `primary` and `primary-foreground` tokens; attack and defense keep their distinct game prompt roles. Arrows, pointer glows, target rings, casting previews, and zone actions share only `targeting.hostile` and `targeting.friendly`. Seat colors remain identity marks. `cardRing` means availability or hover, `cardSelection` means persistent selection, and `zone.*`, `connection.disconnected`, and `cardStatus.summoningSick` are independent roles. The `/card-mock` gameplay fixtures render through the real board overlay using local state and the shared pure dialog/prompt builders.
