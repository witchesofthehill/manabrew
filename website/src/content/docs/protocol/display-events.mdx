Display events are transient semantic facts. The engine decides **what happened**;
the client independently decides whether to render audio, animation, haptics,
accessibility feedback, or nothing. An event never changes authoritative game
state.

## DisplayEvent

`DisplayEvent` is the protocol envelope for transient presentation events. Every
event belongs to a recipient-specific ordered stream outside `GameViewDto`.
Relay envelopes set `forPlayer` and deliver each event only to that seat.

<ProtocolType type="DisplayEvent" />

`sequence` starts at `1` per recipient and increases across every display event.
`count` is a positive semantic quantity. `eventType` identifies what happened;
`origin` and `context` carry optional presentation data.

The same semantic event may drive several independent presenters. For example,
`game.card.play` can trigger both a card flash and an audio cue. Producers do not
emit separate audio and visual variants for the same action.

## DisplayEventType

`DisplayEventType` is an extensible string, not a closed enum. Producers should
use the standard identifiers below. Private extensions should use a reverse-DNS
or other collision-resistant namespace. Consumers must ignore identifiers they
do not recognize.

<ProtocolType type="DisplayEventType" />

## DisplayEventOrigin

`origin` optionally identifies the player or card most closely associated with
an event. It supports spatial audio and local emphasis without exposing
information the recipient could not otherwise see.

<ProtocolType type="DisplayEventOrigin" />

## DisplayEventContext

`context` optionally carries recipient-visible card, turn, or prompt details.
Card and turn contexts drive visual presentation. Prompt context carries the
`promptId` used to suppress repeated presentation of the same open prompt.

<ProtocolType type="DisplayEventContext" />

## Standard identifiers

Manabrew's card-play, turn-start, and prompt events.

### Scripted effects

| Identifier | Forge type | Producer |
| --- | --- | --- |
| `game.card.scripted-effect` | `ScriptedEffect` | Spell resolution or land entry when Forge resolves a card-specific sound resource. |

The client maps `game.card.scripted-effect` to a generic bundled cue. A producer
never sends filesystem paths or card-provided filenames to the client.

## Producer requirements

- Emit events from authoritative engine events, in recipient-visible emission order.
- Start `sequence` at `1` for each recipient and increase it for every delivered
  display event.
- Set `count` to a positive integer. It may aggregate equivalent events that
  happen together.
- Send prompt events only to the player who must respond. Use prompt context so
  clients can suppress repeated delivery of the same open prompt. Emit
  `prompt.action-rejected` for every rejected submission, including repeated
  submissions for the same prompt.
- Do not emit display events while reconstructing or replaying a state snapshot.
- Omit `origin` and `context` when either would reveal hidden information.

## Consumer requirements

- Treat display events as optional presentation. Never infer or mutate game state
  from them.
- Ignore unknown `eventType` values without failing the display stream.
- Ignore an event whose `sequence` is not greater than the last sequence already
  handled for that recipient.
- Use `eventType` and prompt context together to avoid notifying twice for the
  same open prompt. Do not suppress a later `prompt.action-rejected` event for
  that prompt.
- Apply audio and visual presentation independently. Local audio policy includes
  muting, cooldowns, voice limits, and asset selection. `count` is a semantic
  quantity, not a playback command.
