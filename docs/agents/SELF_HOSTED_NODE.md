# The self-hosted node (`manabrew-rs/crates/self-hosted-node`)

Headless engine node (AI bots, automation).

The relay is the source of truth for which game a room is running: the node tags its engine session with the relay's `game_id` and aborts the session as stale whenever the relay contradicts it (room back in Lobby, or `GameStarted` for a different game); a superseded session finishing late never clears its successor's state or ends the relay's current game (the `networking-tests` crate pins this and the other disconnect/cleanup/reconnect contracts end-to-end, one Given/When/Then per test; build-checks CI runs it serialized).

Reconnects to the relay with backoff instead of exiting on socket loss, and resumes its room (`ResumeRoom` + snapshot re-broadcast from `HostSnapshot` in `host.rs`) so a relay restart doesn't kill hosted games. The bot client (`manabot::run_bot`) reconnects the same way: it retakes its seat via `JoinRoom` and pulls `RequestResync` to resume mid-game.

The published `manabrew-node` image is built on **Oracle GraalVM with `--gc=G1`** (`GRAALVM_IMAGE`, `FORGE_GC`), `--features graal-forge`, not `java-forge`: `native-image` compiles the harness to `libforgeharness.so` and the node calls it in-process, so the image ships no JVM and none of the `SELF_HOSTED_NODE_JAVA_*` knobs below apply to it (nor does the GC-log metrics pump — `record_jvm_gc` stays at zero, and `manabrew_node_jvm_*` is therefore a java-forge-only signal that reads as silence on the fleet that actually serves players). The graal isolate reports its own instead, through `forge_gc_stats`: `manabrew_node_engine_gc_collections_total`, `manabrew_node_engine_gc_pause_millis_total`, `manabrew_node_engine_heap_used_bytes` and `manabrew_node_engine_heap_max_bytes`. **The collector counters are Serial-only and publish nothing at all on the shipped G1 image.** Substrate registers `GarbageCollectorMXBean`s for its Serial GC ("young generation scavenger", "complete scavenger") and not for G1, so on a G1 node `getGarbageCollectorMXBeans()` returns an empty list and no collector series exists. That is worse than a zero, because `max by (instance)` drops a node with no series instead of drawing a flat line, so a G1 rollout reads on the dashboard as GC going away. Ask `manabrew_node_engine_stall_millis_total` instead. It is collector-independent: a probe thread inside the isolate sleeps a fixed tick, and a thread cannot be resumed during a stop-the-world pause, so sleep overshoot is time the engine was stopped. `rate(manabrew_node_engine_stall_millis_total[5m]) / 1000` is the fraction of wall clock lost, the figure that identified #684 at 89%, and anything sustained above a few percent is that failure again. It counts scheduler preemption too, so it reads slightly high: on one local Serial run it reported 1625ms against the beans' 1358ms. `manabrew_node_engine_stall_max_millis` and `manabrew_node_engine_long_stalls_total` (overshoot of 100ms or more) carry the tail. A dedicated thread samples `forge_gc_stats` every 15s rather than the decision path doing it, because a node that is stalling is exactly the node that stops completing decisions; sampling per decision made an idle node and a wedged node look identical, both silent. Note that one isolate hosts every room, so a collection stops all of them together — the pre-graal argument that a stall confined to one room rules out shared-resource causes does not survive that change. `SELF_HOSTED_NODE_SHARED_ISOLATE=1`, the image default, hosts every room in one isolate so the card database is loaded once per node rather than once per game; measured 534MB RSS with the database resident and a game live, against roughly 600MB for each JVM the other backend spawns. Serial is native-image's default and all Community Edition offers — `native-image --help` there lists only `serial` and `epsilon` — and a Serial complete collection traces the whole live set, here roughly 450MB of card database that never becomes garbage, at about 1.3ms per MB whatever it reclaims. That is #684: fixed once by naming G1 on the JVM (#691), then reintroduced unnoticed by the move to a native image. G1 is Linux AMD64/AArch64 only, so macOS desktop builds stay on Serial and cannot reproduce fleet GC behaviour; Oracle's base is Oracle Linux 10, whose glibc needs `x86-64-v3`, so the amd64 image can no longer be built on Apple Silicon either and that build is CI-only. The isolate's max heap is an absolute `-R:MaxHeapSize` (`FORGE_MAX_HEAP`, default 1100m) rather than a percentage: `-R:MaximumHeapSizePercent` is rejected outright under G1 ("can only be used together with the serial ... or the epsilon garbage collector"). **It must therefore be kept in step with the container's `mem_limit` by hand**, which the percentage used to do automatically, and leaving it unset is unsafe because G1 defaults to 25% of RAM — about 512MB on a 2GB limit, below the live set. The percentage has to leave room for what the cap does not bound — RSS follows committed heap rather than the live set, and image heap, GC bookkeeping and thread stacks sit outside it — because the cgroup pays for all of it: at 70% of 2GB the node reached its limit and sat in permanent reclaim, swapping, with no OOM kill and no alert (#729). **`SELF_HOSTED_NODE_SHARED_ISOLATE=0`, the historical isolate-per-game shape, is now ignored with a warning rather than honoured.** G1 permits one isolate per process and aborts on the second (`guarantee(SVMIsolateData::_heap_base == nullptr) failed: G1 doesn't support multiple isolates at the moment`), and the collector is fixed at image build and cannot be read back at runtime, so honouring it would mean a guarantee failure on the second room instead of an error anyone can act on. **Decision latency is split by room shape, and the shape is the whole story.** `manabrew_node_forge_decision_seconds` is a histogram labelled `seats`, recording the rules work between a seat answering and the next prompt appearing. It carried a `bots` label until that label was found to read zero on every series it ever produced: it came from the engine's own AI seat list, which is empty for hosted games because bots join as ordinary relay clients, and only the relay knows which seats are bots. Read the histogram over a 30m window: `histogram_quantile` interpolates inside a bucket, so a quiet 5m window holding 15 decisions makes its single worst one the p99, which is how one decision between 2s and 5s once drew a 4.58s peak. Measured over two days of production captures: four seats with three bots ran a p99 near 2.9s with 2-5% of decisions over two seconds, while 2p/1bot, 2p/2bot and 4p/2bot all sat at a p99 of 0.35s with none over two seconds. It is not seat count on its own, since 4p/2bot is clean, and it is **not** bot thinking time, which is a p99 of 0.75s in exactly those rooms. A fleet-wide quantile averages the many clean rooms against the few bad ones and shows neither, which is why this label exists. The older `manabrew_node_forge_decision_stage_seconds` stays, unlabelled, as a summary: its quantiles are per process and cannot be aggregated across instances, so `max by (stage)` over the fleet was never a fleet p99. Keep it only for history from before the histogram. A decision at or above 10s also logs `slow engine decision` at WARN with `game_id`, `seats`, `bots`, `elapsed_ms` and the prompt type, because the metric can say a node was slow but never which game, and finding one otherwise means replaying captures by hand.

`SIGUSR2` writes an hprof dump of the shared isolate to `SELF_HOSTED_NODE_HEAP_DUMP_DIR` (default `/tmp`); the image is built `--enable-monitoring=heapdump` for it. `SIGUSR1` is drain, not dump.

Forge deck launch preserves each card's set code, collector number, and foil finish through `CardIdentityForJava` and `ManaBrewEngineAdapter.cardRequest`. Do not reduce that boundary to name plus set: Forge can select another art in the same set, and the resulting battlefield snapshot no longer matches the deck.

Under the `java-forge` backend, `SubprocessBridge::spawn` sizes the engine JVM explicitly (`SELF_HOSTED_NODE_JAVA_HEAP_MB`, default 1024; `SELF_HOSTED_NODE_JAVA_ACTIVE_PROCESSORS`, default 2; either set to `0` to fall back to JVM ergonomics; `SELF_HOSTED_NODE_JAVA_GC_LOG` = `stderr` or a directory, for `-Xlog:gc*`; `SELF_HOSTED_NODE_JAVA_OPTS` appended last) — a fleet runs dozens of these side by side and every JVM would otherwise size its heap and GC thread count from the whole machine (#684). `-XX:+ExitOnOutOfMemoryError` is always set; the endstep concurrency patches assume it. Prefer `stderr` in a container: alloy ships container output to Loki and nothing ships files, and the subprocess owns stdout for the protocol. GC lines are forwarded at `info` (the rest of the engine's stderr stays at `debug`). When setting `SELF_HOSTED_NODE_JAVA_HEAP_MB`, raise the container's `mem_limit` with it — the heap cap does nothing if the cgroup kills the process first, and the JVM's non-heap plus the node itself need roughly another 500MB.

A background `updater` monitor (`updater.rs`) polls the version manifest (default `play.manabrew.app/manifest.json`) and compares its own `CARGO_PKG_VERSION` against `packages["self-hosted-node"]`; when behind it logs a warning, or — with `--shutdown-on-stale` / `SELF_HOSTED_NODE_SHUTDOWN_ON_STALE` — gracefully cancels its rooms (relay sockets get a proper WebSocket close) and `exit(0)`s once idle (no `engine_session` active in any room) so a pull-on-restart supervisor respawns it updated. SIGTERM/SIGINT trigger the same graceful room shutdown. Do not enable the flag under plain `restart: unless-stopped` (re-runs the same image → crash loop); it needs a supervisor that pulls latest on restart.
