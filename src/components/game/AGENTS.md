## Board canvases — separate desktop and mobile scene roots

`GameBoard` selects exactly one composition root: `DesktopGameScene` or `MobileGameScene`. Each root owns its Pixi scene lifetime and overlay scene. Desktop constructs `DesktopBoardScene` through `DesktopBoardCanvas` and `DesktopPromptLayer` through `DesktopBoardOverlayCanvas`; mobile constructs the corresponding `Mobile*` classes. Mode changes unmount one root and create the other. Never toggle a live scene between desktop and mobile, import `BoardCanvasSurface` or `BoardOverlayCanvasSurface` from feature code, or add mobile state to `GameBoard`. Mode-specific layout and rendering policy belongs in the matching `Desktop*Presentation` / `Mobile*Presentation` or `DesktopBattlefieldLayout` / `MobileBattlefieldLayout` file; shared board, region, canvas, and prompt classes consume those policies and must not regain a desktop/mobile flag.

- **Regions** (`BoardRegion`) own per-player grid layout, attachment stacking, rings, combat staging, and animation. The local region gets full interaction (drag/marquee/overlay); opponent regions are tap-to-target + hover only. Each reaches orchestrator services through a `RegionHost`. Combat attack rows always use the theme's hostile `promptAction.attackAction` colour and carry no redundant player identity caption. Their inner-edge chevrons point toward the opponent, defense connectors use `promptAction.defenseAction`, and attackers with multiple assigned blockers receive a numeric defense badge.
- **Local controllers** live on the scene: `HandController`, `SelectionController`, `BattlefieldOverlay`, plus the `DragHandler` gesture. They talk to the scene through the `HandHost` / `SelectionHost` / `OverlayHost` seams in `@/pixi/board/types`.
- **Arrows + the spell stack + engine prompts** are not drawn inside the board scene. Each composition root owns one transparent overlay canvas above the React panels. The desktop overlay constructs `DesktopPromptLayer`; the mobile overlay constructs `MobilePromptLayer`. Both share stack, arrow, preview, and prompt mechanics, but presentation identity is fixed at construction. The scheduler samples `BoardScene.getArrowDefs()` while arrows, image loads, stack tweens, previews, or animated prompts are active, then sleeps. The canvas is `pointer-events: none` except while the cursor or a routed touch is over actual stack, prompt, or preview content.
- **Prompt tween lifetime** follows the Pixi subtree. `PromptLayer` destroys the previous modal during prompt rebuilds; any GSAP tween targeting a modal `Container` must be killed when that container is destroyed, because Pixi clears its transform before the next lazy GSAP render.
- **Overlay disposal unpublishes before destroying.** Clear the owning instance's React-facing layer, scheduler and app refs before Pixi teardown; child destruction can emit callbacks or throw. Leaving refs published lets later effects update a half-destroyed stack whose transforms are already null.
- **The shared board-canvas callback proxy is explicit.** Every callback added to `GameCanvasCallbacks` must also be forwarded through the object passed to the scene factory; adding it only to the type and React producer silently drops the event at the canvas boundary.
- **React-driven Pixi setters must stay callback-free.** `BoardCanvas` applies `zoneTiles` from a React effect, so `BoardZoneTiles.setSpecs` must not re-emit hover callbacks for an already-hovered tile; callback-driven React state would recreate the specs and form an infinite render loop. Hover callbacks belong to pointer transitions.
- **Journal rows are display-only.** A row's title is the first line of `CheckpointDto.log` (Forge's public game log produced after that checkpoint), falling back to the decision label or step; the (i) button expands the full lines inline. `CheckpointRow` picks its icon from `checkpointsPanel.utils.ts`, keyed by the labels of the harness `DecisionHistory.description`; a renamed label falls back to the generic icon. Consecutive `Pass priority` checkpoints without log lines collapse into one expandable run, and each inner row stays a rewind target. Seat dots come from `Game.tsx`'s `playerColorMap`. Treat a missing `log` as empty: older engines omit it.
- **Expanded action panel owns the top live-game layer.** `RightActionPanel` uses `z-[9001]`, one level above the live `BoardOverlayCanvas` wrapper at `z-[9000]`, so Journal and Dev cover the action prompt instead of the prompt bleeding through the panel. Portaled modal previews remain above both.
- **Layout** keeps the local player along the bottom. The default **focused** layout gives opponents fixed, overlapping play rectangles across the top; moving delimiter masks reveal one field without re-gridding its cards. When combat or targeting expands multiple opponents at once, each participating grid fits its delimiter target band. That band layout is temporary: `BoardRegion.setGridBand` saves the full-width card slots, zone-tile slots, and overflow stacks on entry and restores them on exit, because slots are stored as grid column/row indexes and a narrow band's indexes would otherwise pin cards to the left of the full-width grid. Optional **overview** assigns opponents full-width horizontal bands and fits each grid to its actual band height. Compact screens retain focused layout. Each playmat fills its complete region to the viewport edges; only the center phase strip and explicit hand, HUD, and combat reservations reduce card placement space. `computeBoardLayout` owns the base rectangles; `DesktopBattlefieldLayout` and `MobileBattlefieldLayout` own their distinct scale solves.
- **Delimiters live in `BoardScene`.** In focused layout, `delimCurrent`/`delimTarget` partition the canvas into non-overlapping clip bands. `BattlefieldDividers` owns shared fog gradients, glow and particle animations used by both the gameplay board and Limited accordion. Manual field selection takes precedence; unlocked pointer hover can focus any opponent during combat or targeting. Without hover, targeting and combat participants take precedence over the active turn. Combat selection, hand drag, and inspection lock hover-driven refocusing; targeting does not. Overview bypasses delimiter easing. Reduced motion snaps delimiter changes.
- **Touch input.** All gestures are pointer-event driven. `LongPressGesture` (`@/pixi/LongPressGesture.ts`) keeps long-press as an optional sticky-preview shortcut on Pixi card surfaces: battlefield sprites route through `BoardScene`, stack cards through `StackCardSprite`, prompt source/cards through `PromptLayerBase`, and zone-browser cards through `DialogCardPickerScene`; all reach the same `Game.tsx` preview state used by desktop card hover, so the persisted printed/rules preference applies consistently. Neutral battlefield and hand card taps open that sticky preview too. `BattlefieldOverlay` action controls sit above their card sprites, own only their visible geometry, and stop the card-body gesture; full-card selection overlays may route through `BoardScene.beginBattlefieldCardPress` because an explicit selection prompt owns the whole card. Inactive action overlays must disable their event subtree immediately even while the visual fades out. The release-tap is swallowed (`consumeTap`) so a hold never triggers a tap action, and the board stage swallows every `pointertap` whose pointer was promoted into a pinch. Every hand card enters `useHandDrag` (document-level `pointermove`/`pointerup`/`pointercancel`, filtered by `pointerId`): a stationary release opens the preview, release over the hand lets `HandController` commit its Pixi insertion slot, release over the battlefield casts only when the card has a direct cast action, and touch hold tears the drag down for the same sticky preview. `useHandOrder` owns the client-only stable ID order; the cog-opened `GameSettingsModal` changes the persisted Manual/Color/Mana value mode without touching engine snapshots. DOM card chrome (`CardImageThumbnail`) uses `useLongPressPreview`.
- **Hover detection** is owned by `BoardScene`. Focused layout checks the cursor against delimiter bands; overview checks both coordinates against the opponent's rectangle. Region highlights use the player's seat color and report `onHoverOpponent`. Hand exit detection also reconciles against document-level pointer movement because overlay ownership can suppress Pixi stage moves. DOM hand-action hover holds must release when their conditional panel unmounts. While the Pixi ticker runs, Pixi's `EventTicker` re-dispatches a synthetic `pointermove` at the last cursor position every tick, so a stationary cursor re-hovers its card continuously; `CardPreviewMachine.hoverStart` therefore keeps a pending delayed show for the same card instead of restarting its timer.
- **Keyboard and screen-reader semantics stay React-owned.** `GameBoardAccessibility` mirrors players, hand and battlefield cards, direct mana actions, stack objects, zones, and phase stops as native controls while the Pixi canvases remain visual/pointer surfaces. Global `useKeybindings` preserves native Enter, Space, and navigation-key behavior when focus is on a control.
- **Pixi player HUD + on-grid zones**: the player panel is **all Pixi, always on** — there are no React player panels (the old `PlayerPanel`/`PlayerAvatar`/`BadgeOrbit`/`ZoneActionColumn` chain and the `pixiPlayerBar` pref were removed). It lives in `@/pixi/hud/`:
- **`PlayerHudLayer`** owns one **`PlayerHudCapsule`** player plate per seat and a shared tooltip. Desktop horizontal plates use a fixed 58px row showing avatar, life, hand count, and compact state icons. The game menu's settings cog lives in the desktop action-cluster header, not on the player plate. The entire player plate uses a pointer cursor and opens `PlayerSheetModal`; while the player is a legal target, the same full hit area targets them instead. Targetability and selection highlight only the avatar border, never the panel bounds. Player names and textual turn/priority labels do not render on the plate. Life sits immediately right of the avatar, then hand count. The hand count's three-card fan draws an opponent's revealed hand cards (Forge `canBeShownTo`, e.g. Telepathy) face up and the rest as backs; `PlayerSheetModal`'s hand tile shows the whole hand the same way as a `HandCardStrip` and opens it in the zone viewer. The vertical divider renders only when a state icon follows it. Player plates have no background surface, perimeter, or seat-color rail; only their controls and state marks draw chrome. Mana floats on its own compact tray above or below the plate rather than stretching the player plate.
- **Collapsed opponent panels** render only live resources: the mana tray is absent when every mana value is zero, and the status tray is absent when no player-status badges exist. They do not render a Details/overflow control because the whole player plate opens `PlayerSheetModal`.
- **Opponent hand fans** (`OpponentHandFan`, owned by `BoardScene`) hang from the top edge of each expanded opponent band: the local fan's layout mirrored vertically, at `OPPONENT_HAND_SCALE` and mostly off-canvas (`OPPONENT_HAND_SINK_FRAC`). Hovering a card drops it into view; revealed cards draw face up, open the card preview, and on click open `CardInspectModal` (via `onInspectCard`); hidden cards are backs (`GameBoard` pads the visible `hand` to `handCount` with `hiddenZoneCard`). The fan clips to the opponent's region band, not the inset playmat rect, so its cards run off the canvas edge like the local hand. The persisted `opponentHandFan` preference (Board settings: Always / Only when revealed / Never, default Only when revealed) filters in `GameBoard`: a revealed fan shows the whole hand, backs included, once any card in it is visible. Collapsed bands hide the fan, the fan reserves no grid space, and only the desktop presentation shows it (`showsOpponentHands`).
- **`BoardZoneTiles`** renders library, graveyard, exile, and command on reserved grid cells, plus the Attraction deck (a face-down pile like the library) and the junkyard (a public pile like the graveyard) only while each holds cards. Library, graveyard, and exile default to successive rows in the first available column; each region persists its selected fallback cells across relayouts, and explicit local drags update those same slots. Library keeps its offset pile silhouette with dark separators, while the Scryfall card-back JPEG is clipped to the shared card radius because its source pixels are near-white outside the printed rounded corners. Nonempty public zones show their top card and count. Empty graveyard and exile zones retain dotted card-slot outlines around their subdued glyphs and labels; all empty zones keep bounded hit areas. Clickable tiles fade in the shared `cardRing` glow with GSAP on pointer hover. Empty-tile ambience uses additively blended Pixi `Graphics` advanced by the existing `BoardRegion.animate` tick: library page wisps rise, graveyard ash settles, exile motes orbit a void ellipse, and command sparks circle a seat-coloured sigil. Any tile showing a card replaces particles with a layered magical glow pulse beneath the card perimeter. Hovering a populated command tile opens every command card in one pointer-traversable overlay group. That group follows the global in-game printed/rules preview preference and keeps the shared preview machine's tile-to-preview hover grace. Ambient effects mutate transforms and alpha only and disappear when animations or reduced motion disable motion. An opponent tile in the synthetic attack-row slot uses the stable full-field playmat rect so its complete card footprint remains inside the playmat border as delimiter bands resize. Opponent tiles remain non-draggable. `BoardCanvas.zoneTiles` is the only zone state bridge into Pixi.
- **Keep-outs** use the local player's rendered plate, each focused opponent field's stable expanded-plate footprint, the visible desktop hand strip, and the measured closed `MobileHandControl`. Opponent delimiter hover changes only clipping; it never changes grid blockers or repositions battlefield cards and zone tiles. Floating mana, action prompts, and prompt-info popovers overlay the battlefield without claiming grid slots or triggering a re-grid. `HandController.getBlockerRect` is root-local and independent of current hover/drag. Desktop grid reserve and hand blockers use `HAND_RESERVE_TRIM`; compact hand sheets contribute no battlefield reserve, while their closed React control contributes its own padded blocker. Grid debugging draws legal card slots and blocker rectangles separately; it does not render blocked cells as card-shaped placement options.
- **Hand/action clearance**: the desktop hand never pushes the local player plate or the full action panel up. The hand host insets the hand zone by the plate's minimum width on the left and by the action panel on the right (`DesktopBoardScenePresentation.handInsets`), and `HandController.getDimensions` caps the card spread so any hand size fits that zone; large hands overlap more. The overlay reports the panel's screen bounds through `BoardScene.setActionPanelBounds`. A modal prompt keeps the last panel bounds, so the fan does not resize between prompts. Full tablet panels stay bottom-right with a 320px width cap; compact panels follow `mobileHandedness`. Full tablet priority controls omit keyboard hints and use a skip-forward icon when the end/next-turn or resolve-stack label would force a second row, preserving its accessible title. Their priority-mode toggle is icon-only: hand for full control, lightning for autopass, with a touch-sized target and accessible mode description. Unfolded phones use the same mobile scene and overlay as phones; scene selection follows `useIsMobileGame`, not viewport height alone.
- **Mobile scene ownership** (`useIsMobileGame` selects `MobileGameScene`; desktop state and scene instances are not retained):
  - **Phase strip** (`@/pixi/PhaseStripLayer`): desktop retains its 30px center band. Full tablet strips use caption-sized labels and desktop-density 32px cells and per-seat width reservations rather than the enlarged tablet control metrics; phone controls keep their touch sizing. Expanded rows float over the board. Compact reserves no persistent center band or divider line and hides the canvas strip entirely. A pill using the same phase-strip surface, short label, and active-player border sits right of the local player plate (`compactPhaseControl.anchor`, fed from `BoardScene.getLocalCapsuleBounds()`, with the action cluster as fallback). While the current step matches one of the local player's armed stops, `compactPhaseControl.pulse` makes the pill fire a single expanding ring in the active seat colour. Tapping it opens the React-owned `MobilePhaseStops` bottom sheet. The sheet exposes each combat substep and other non-untap stops independently, with horizontally scrollable 48px segmented cells, active-phase border, and per-seat stop indicators without reflowing the board. Player plates do not repeat priority.
  - **Action cluster** (`@/pixi/prompts/PromptLayer`): native Pixi buttons use explicit hit areas, pointer states, accessibility metadata, and semantic `promptAction` colours. Desktop includes the mode and board-menu controls. A conditional info button immediately left of the mode control opens prompt instructions and combat details in a popover, so optional context never changes the visible cluster height. Pay-mana prompts keep only payment actions in the cluster; the source card, cost description, pool status, and payment guidance live in the info popover. Compact removes the panel surface, glow, and header; keeps the current actions and board-menu trigger pinned to the bottom corner named by the `mobileHandedness` preference (`usePreferencesStore`); hides while the board is dimmed; and opens the same context popover on long-press. Compact priority views keep the cluster to one 44px-high row: a wide Pass button, an orange skip-forward icon action, then the AUTO/FULL toggle and settings cog side by side with independent 44px touch targets. Two stacked 44px controls would double the cluster height. The toggle uses the same `fullControl` preference as Tab; no-action views retain the same utility pair. Action-panel bounds (plus the anchored phase pill's rect) are used only for overlay hit-testing and never contribute battlefield exclusion zones.
  - **Hand** uses inline presentation on desktop and a transparent overlay in compact mode. A closed compact hand has no Pixi visibility, but its measured control reserves a bottom strip (`getHandReserveBottom` in compact reads the padded `MobileHandControl` height, sticky across open/close) that sizes the card solve while the local grid itself spans the full field: bottom-anchored rows clear the attack band and deliberately run beneath the plate, hand control, and action cluster, which draw over them; `MobileHandControl` opens the same `HandController` above the battlefield, with an invisible full-screen hit target behind the fan for outside-tap dismissal. The open phone fan uses its own wider spread so overlapping cards retain more artwork and playable rings, and while it is open the compact action cluster and phase pill yield to it (`dimmed` on the compact prompt spec) except during put-back selection, whose confirm stays reachable; during the mulligan decision the keep/mulligan buttons render in the hand chrome above the fan instead. Keep `MobileHandControl` inside the battlefield stacking context: engine prompts, stack content, and card previews belong to `BoardOverlayCanvas` and must render and receive pointer input above it. Its icon reuses the three-card-back fan from `PlayerSheetModal`. The control is transparent and borderless so it reads as a playmat-edge tab rather than a web pill; its quiet bottom rule expands and glows with `cardRing` only when a hand card is playable or activatable, and its open-state dismiss button follows the same `mobileHandedness` corner. Pressing the collapsed hand pill peeks the fan at full height and releasing sinks it again. The mulligan decision opens the hand on arrival. Mulligan selection forces the hand open. Tapping a playable hand card takes its available cast or action path, dragging it onto the battlefield preserves direct permanent placement, and tapping a non-playable card inspects it. While a drag is in flight the fan never sinks, reshapes, or replays its entrance — it stays fixed so the dragged card can be positioned freely; the fan only moves when the authoritative state changes (a drop, a reorder, or a cancellation returning the card). Long-press remains the sticky inspection shortcut through `useHandDrag`. A new engine prompt closes the hand unless it is a mulligan decision (which opens it) or mulligan selection owns it. Opening player or phase-stop inspection dismisses the hand and sticky card preview; opening a sticky preview closes compact board chrome.
  - **Player plates** use one 36px horizontal capsule in compact mode with only avatar and life. Compact omits hand count, state icons, the life label, and floating mana; detailed state remains in `PlayerSheetModal`. Opponent plates align inside the playmat's top-left corner. The local plate is pinned to the playmat's bottom-left corner independently of the compact hand sheet and its centered control. When a hidden zone contains an available action, the avatar pulses with `cardRing` until the player opens the sheet.
  - **Zones leave the Pixi grid and persistent battlefield chrome in compact mode.** Touching an opponent field makes it the focused expanded field; do not add a separate compact field switcher. Tapping a player capsule opens `PlayerSheetModal`, where library, graveyard, exile, and command actions remain available. Each hidden-zone resource control inherits its zone tile's actionable or targetable colour and glow, so available actions remain visible without persistent battlefield tiles. Opening the zone preserves the cue on each legal card through `CardSprite.setPlayableRing`. Command tiles show the snapshot's optional `commanderTax`; never derive it from mana cost or local cast history.
  - **Row fitting** is selected by `battlefieldLayoutPolicy`: compact gives the local field 60% of available height for three local rows and two opponent rows; if that would make square cards narrower than 64px, it gives each field 50% for two rows apiece. Turn, targeting, focus, and combat state must not change that split or rescale either battlefield. Compact opponent and local fields meet at the center seam, share one card scale (the smaller solve) so self and opponent attack rows match, and anchor the local grid to the bottom of the full field so the rows clear the attack band, with the bottom row allowed to run beneath the reserved strip's controls. Combat is an overlay rather than a layout mode: staged and live combat cards center on that seam without reserving a lane or reflowing the normal grid. Desktop keeps its combat band permanently reserved, an even field split, the three-row baseline, and two-row largest-card ceiling. Default placement matches desktop on every viewport: creatures claim the combat-side row, other permanents fill the rows above the land row, and lands always hold the rear row; manual moves still take precedence.

At the default multiplier, square cards are at most `GAME_CARD_SIZES.battlefield.width` (70 CSS pixels); row fitting can make them smaller. Short phone layouts keep their existing row-based size.
  - **Compact overflow is semantic and deterministic.** Preserve pending drops, explicit player placements, and one visible anchor per card category whenever capacity allows. Collapse auto-placed lands first, then other permanents, then creatures. Attach overflow to a visible card from the same category when possible; if no such keeper fits, attach it to a visible keeper from another category so every card remains accessible through a stack badge. The host's stack-count badge reports the complete pile.
  - **Compact battlefield cards use a square footprint.** Original and generated styles fill that tile from the top of the card face, keeping the title and artwork while cropping the rules area; art-forward uses source artwork and compact overlays. Mana tap overlays cover the full card on desktop and compact layouts and forward presses into the board drag gesture, so a tap activates mana while a drag still moves the card. Compact untap overlays also fill the square card; desktop untap controls remain inset on portrait cards. The player's `battlefieldCardStyle` selection still applies on every viewport, full card inspection remains rectangular, and desktop battlefield cards keep the printed aspect ratio.
  - **Touch card input** uses neutral battlefield and non-playable hand taps for sticky inspection; playable hand taps and explicit battlefield controls perform game actions. An engine selection prompt may temporarily claim the full card hit area because the interaction mode is explicit. Hand, battlefield, stack, and prompt cards all feed the same `preview.showSticky` path used by desktop hover previews; sticky previews bypass prompt-only hover suppression and preserve the user's printed/rules choice. Long-press remains an inspection shortcut, touch pointer movement does not drive battlefield or hand hover previews, and `CardPreview` clamps its size to the viewport height in compact mode. Battlefield dragging uses `TOUCH_MOVE_SLOP_PX`, matching long-press cancellation, so ordinary finger jitter remains a tap instead of moving the card. Crossing that threshold lifts the card and reveals one destination grammar: active-action outlines for empty cells, a doubled friendly outline for stacking, and a lethal-colour crossed card for invalid space. Invalid releases restore the authoritative battlefield position instead of snapping to the nearest legal cell.
  - **Compact stack** uses up to 69% of the overlay height, with a 16px top inset and 104px bottom reserve. `StackLayer.cardWidth` shrinks cards as stack depth grows; `stackLayout` anchors the pile above the bottom controls. Only visible stack cards and controls block touches, so empty space in the pile lets a touch focus the opponent field beneath it. Desktop keeps its own 55% height limit and centered offset.
  - **Card-choice scrolling** uses a vertically scrolling grid for mobile `chooseCards` and `revealCards` prompts above `SHORT_SCREEN_MAX_HEIGHT_PX`; short phone layouts keep the horizontal card strip. Keep the source preview beside the prompt, the header and footer fixed, and the grid at its fitted card size rather than scaling the entire list to fit the body. `PromptLayerPresentation.cardLayout(viewportHeight)` selects the layout on each rebuild, including resize.
  - **Player plate tap = inspection.** Every player plate uses one full-panel hit area and opens `PlayerSheetModal` unless that player is currently targetable, in which case the same hit area submits the target.
  - **ManaAbilityTapButton** long-press shows a transient description popover (the hover `title` equivalent). Interactive Pixi-only chrome — the ×N stack badge — grows its hit area to a 48px touch target on coarse pointers (`STACK_BADGE_TOUCH_PAD`); keep any future sprite-level control within the same rule.
  - **Native tap feel** is global CSS, not mobile-gated: `index.css` sets `-webkit-tap-highlight-color: transparent` on body, `touch-action: manipulation` on tappable elements, and the `.game-touch-surface` class (on the `Game.tsx` root and the `Modal` backdrop — modals portal to `document.body`, outside the game root) suppresses text selection, iOS image callout, and image drag ghosts; inputs keep text selection. Optional vibration runs through `haptic()` (`lib/haptics.ts`, gated by the persisted `hapticFeedback` preference and `navigator.vibrate` support): `select` on long-press recognition, `confirm` on battlefield placements and combat assignments, `warn` on a rejected drop. Never delay the action for the vibration.
  - **Priority haptics follow ownership, not prompt IDs.** `Game.tsx` vibrates when priority moves from another player to the local player. Answering an action can replace a prompt while the same player still has priority; that must not trigger another vibration. Gameplay audio and sound settings are left to the separate sound implementation.
  - **Battlefield lab**: `GameDevPanel`'s Player workspace can force every identity, turn, targeting, combat, connection, badge, counter, life, hand, incoming-damage, and W/U/B/R/G/C mana-pool state across every seat. ## Game loading

`GameLoadingScreen` keeps setup progress centered on desktop and portrait screens. Compact touch landscapes use a two-column layout with the status and exit action beside the progress card so the attached `GameLoadingTip` remains visible at short viewport heights. Configure copy, audience, keybinding IDs, cadence, and transition duration in `gameLoadingTips.ts`; keybinding tips render the player's persisted shortcuts, while touch loading screens exclude desktop-only entries.

`useGamePrefetch(mode)` owns `isPrefetchingCards` once the first game view arrives; start flows set it and never clear it on success. Both modes wait for immediately visible printed-card textures. Before clearing the loading flag, both modes render every visible hand and command-zone card in each Manabrew variant in use (rules faces when hand, stack, prompt or preview use Manabrew; full faces when the battlefield does) and set `isRenderingCards`, which advances the loading screen to the "Render Manabrew cards" step. Pre-rendering uses `manabrewRenderVariants` (`lib/cardFaceWarmup.ts`): rules faces at the hand size scaled by `cardSizeMultiplier`, full faces at the battlefield size. `warmDeckFaces` renders the prompt size in a second pass, after every card has its hand-size face. A smaller request takes a finished larger raster as is, or a resized copy of it, instead of composing again. Faces with live highlights are never resized, so only the finished larger raster serves them. An in-game card resolves to its printed face, and so to the pre-render cache key, unless its characteristics changed; `showsPrintedFace` treats Forge naming the card and oracle text saying "this land" as the same text. `GAME_LOADING_CAP_MS` bounds the whole loading wait; when it expires the game opens and the remaining work continues in the background. Then `warmDeckFaces(own, others)` renders every deck-pool card, both faces for double-faced cards, at `background` priority, two in flight and each started from an idle callback, so draws and library reveals read finished faces from the cache. Main-deck cards and commanders go cheapest first, the local player's before an opponent's at the same mana value; sideboards, tokens and other pools follow. A browser-hosted Forge game also knows the local library order: when the local seat is prompted, `SabTransport` posts a `game:library_top` worker event with the identities of that seat's top seven library cards, and `warmLibraryTop` renders them at `visible` priority, rules faces first. When the local hand is still empty at load (Forge deals it after the dice roll), the loading wait also covers that first library top, so the opening hand is ready when it is dealt; `libraryTopRendered` waits at most `LIBRARY_TOP_ARRIVAL_MS` for the event. It is a worker event, not a seat message, so it stays in the hosting tab; never route it to the relay or another seat, because it is hidden information. Hosted nodes and relay guests do not get it. The warm-up starts only from game loading, never from deck selection. It first requests every non-token card's Scryfall data at once, so the lookups share `/cards/collection` batches; the one-card-at-a-time render lanes must not drive the lookups. A newer warm-up supersedes the previous one. Realistic everywhere skips generated-face preparation. Apply the selected hand style before seeding the board scene so the first painted hand already uses that view.

`visible` warms the complete deck pool's printed and `art_crop` textures in the background. `full` additionally waits for those deck-wide textures, unless the battlefield uses Manabrew frames, and publishes `cardPrefetchProgress` for the loading screen's "Load card images" bar. Deck-pool render requests pass `gameplay: true`. `cardRenderSnapshot.ts` resolves a live card that matches its printing to the printed face, so a deck pre-render and the drawn card share one cache key. Keep that equivalence when you change live-face fields, or pre-rendering stops matching. Immediately visible textures and opening-hand faces remain readiness requirements in either mode, within the same cap. A card in Manabrew view never shows its scan or a placeholder while its face renders: `CardSprite` is not drawn until the generated face is ready. `FACE_HOLD_CAP_MS` bounds that hold; past it the themed placeholder with the card name appears, which the warm-up order should make unreachable. The scan appears only after a render failure, inside the rules face for hand-style sprites. `Game.tsx` picks `full` when `preloadCardImages` is enabled, which is the default. Card preparation starts after the first game state arrives and remains the last loading-screen step.

## Modal pattern

All game modals use the `Modal` compound:

```tsx
<Modal onClose={onCancel} maxWidth="max-w-md">
  <Modal.Header>{/* title + optional source-card thumbnail */}</Modal.Header>
  <Modal.Instructions>Instruction text</Modal.Instructions>
  <Modal.Body>{/* content */}</Modal.Body>
  <Modal.Footer>{/* buttons */}</Modal.Footer>
</Modal>
```

Use `Modal.Close` for buttons and `Modal.CloseShortcut` for remappable keybindings that dismiss a dialog so both paths finish the exit transition before unmounting. `Modal` owns the nested-dialog stack, focus containment, topmost Escape handling, backdrop dismissal, reduced-motion-aware entry and exit transitions, and the button-click sound for every button in its panel. Do not add click sounds to individual modal buttons.

Keep app-wide mute and volume controls in the cog menu's separate `SoundSettingsModal`, using the shared `SoundControls`. `GameSettingsModal` owns board and prompt preferences, not audio.

The Modal backdrop follows root `--visual-viewport-*` bounds and safe-area padding. Its body and, under extreme height constraints, the enclosing header/footer column scroll. Keep primary actions reachable without scaling labels. React controls use semantic UI text roles; Pixi keeps its authored desktop sizes and applies `getUiFontFloor` and `getUiControlFloor` as touch-only minimums, with measured geometry and inverse parent-scale compensation for card-attached controls. Card printing remains proportional.

Embedded rules cards receive their stable layout scale through `CardSprite.setHandRulesScale`; it includes ancestor scale before the inner preview transform. Update it with layout targets, not raster polling or animated hand interpolation: changing it rebuilds rules-action geometry. Native card fitting is unchanged.

`PromptModalLayer.createModalShell` owns vertical touch scrolling for overflowing engine prompts, including card choices and reveals. Keep it independent of compact mode: larger touch viewports can still use the desktop scene and need swipes. Scroll gestures cancel card long-press, suppress release taps, and yield to an active card drag.

Card browsers use `DialogCardBrowser`. It keeps search, collapsed type and color filters, sorting, scroll position, keyboard navigation, and per-card view state together. Zone viewers render cards in a virtualized grid through `DialogCardPickerScene`, using the same 964px panel maximum, 16px viewport-height margin, effective 12px card inset, `fitPromptCardDimensions`, orientation-aware scale, `PROMPT_CARD_GAP`, and `PROMPT_CARD_ROW_GAP` as `chooseCards` and `revealCards`. Do not add captions beneath picker cards because they change the shared row pitch; card names remain available through the card face and accessible option label. Landscape cards retain the portrait scale instead of fitting their long edge into a portrait slot. Keep every card at full opacity and activate legal direct actions without an extra tray confirmation; manual moves retain the explicit footer action. Hover and keyboard focus use the same shared `gameTheme.cardRing` hue, with clicked or selected cards allowed to strengthen that ring without recoloring it. After changing a picker card's scale, call `syncHandControlsScale`; otherwise its view and face controls inherit the card scale until a face toggle reflows them. Keep `CARD_BROWSER_HORIZONTAL_PADDING` and `CARD_BROWSER_VERTICAL_PADDING` in `cardBrowser.ts`; the React accessibility controls and Pixi scene must use the same cell geometry and the shared centered row offset computed from the actual number of cards in each row.

## Card rendering ownership

Four renderers draw cards. `components/game/cardPresentation.ts` provides shared data for type lines, counters, state, costs, progression, and stats. Each renderer draws that data itself. `HandRulesCardFace.ts` is an adapter, not a fifth renderer.

| Renderer                                      | Tech | Where it shows                                                                                                   |
| --------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------- |
| `@/pixi/CardSprite`                           | PIXI | In-game battlefield + hand (the real game)                                                                       |
| `components/game/BattlefieldCardFace`         | DOM  | Custom battlefield styles (art-forward / mini-frame), settings preview, and dev gallery (`/card-mock`)           |
| `components/game/CardPreview`                 | DOM  | Printed-card hover preview in-game and across deck/editor surfaces                                               |
| `@/pixi/cardPreview/RulesCardPreviewLayer.ts` | PIXI | Every rules card: board hover plus embedded hand, prompt, and stack views through `HandRulesCardFace.ts` adapter |

**Rule:** when you add, restyle, or remove a card visual — counters, damage wash, summoning-sickness, P/T coloring, frame tint/bars, keyword chips, mana pips, foil, badges, etc. — change **every** renderer that should show it, in the same commit. A change that lands in only one drifts the others (this has bitten us repeatedly: FPS-style regressions, counter display, damage-wash corners, summoning sickness).

- **Shared, theme-driven color math lives in `@/themes/gameTheme.ts`** (`frameTint`, `readableTextColor`, `withAlpha`, `darken`, `relativeLuminance`). Use these in both DOM and Pixi instead of re-deriving — that's what actually keeps the look identical across renderers. No hex literals (see Theme below).
- **Geometry must match too.** A full-card overlay must trace the card's rounded corner: in the DOM the card border is drawn as an `inset-0 rounded-[inherit]` overlay (not a CSS `border`) so washes can fill to the outer radius; in Pixi the equivalent is a `roundRect(..., CARD_RADIUS)`.
- **Use `PtBadge` for realistic P/T badges.** `Card` and `CardPreview` place it at the bottom right. Size it with container units (`cqw`) and `em` so stacks, modals, zones, and hover previews keep the same proportions. The card root must set `@container`. Do not add another pixel-sized P/T span. Printed hand faces already include P/T in the image; `HandRulesCardFace` puts the live value in its footer. Every battlefield style calls `CardSprite.updatePT`. The card DTO must retain `types`, effective `power` and `toughness`, and printed `basePower` and `baseToughness` so each renderer can derive the same P/T color.
- **Attacking + summoning-sickness now match the DOM in Pixi too:** both draw an inset **edge glow** (`CardSprite.updateEdgeGlow`) — red for attacking, frosty + pulsing for summoning-sick (pulse driven per-frame by `BoardRegion.animate` → `tickEffects`); summoning-sick also keeps the grey desaturate/dim filter. Pixi's `setRing` is now reserved for **interaction/combat** states only (lethal, pending, tappable/untappable land, selectable/targeting).
- **Known intentional divergences — do not "fix" without being asked:** some effects are **Pixi-only** (doomed wash, foil ring, ring-bearer, status badges `MORPH`/`EXERTED`/…, damage-order badge, stack count). The DOM face also currently lacks the _debuffed_ P/T color that Pixi has.

`CardSprite.printedFaceContainer` holds the source image, mask and placeholder; opaque foil/wear renders above that image but below `printedChromeContainer`, which holds live stats, counters, damage, rails and badges. Both printed containers share visibility and the content-surface flip transform. Preserve this order when embedded Rules faces append or reorder their layers.

Artwork commits recalculate caption clearance and counter positions together; switching back to scans or losing the texture clears that reserve. DOM damage washes sit above opaque finish canvases and live-ink layers, below gameplay badges.

Rules that preserve fixed behavior:

- **Never unmount the preview on transient state.** Engine prompt churn (a prompt answered and replaced within a frame) must not blink the DOM: pass `suppressed` to `HoverCardPreview` (opacity fade; hover state survives) instead of adding conditions to the mount gate. Unmount-gating on `promptType` is exactly what caused the show/hide/show flash.
- **Explicit UI takeovers dismiss.** Zone viewer, ability picker, hand drag: dismiss via the hook's `dismissDeps` argument or `dismiss()` (synchronous — never `setTimeout(dismiss)`).
- **Zone viewer inspection stays in its modal.** A sticky card preview triggered from the zone viewer portals into the top modal panel so its printed image and Pixi rules canvas clear stacked backdrops while retaining the modal's focus trap. Ordinary board hovers remain suppressed while the viewer is open.
- **Instant card-switching is only allowed while `open`.** A dismissed preview re-enters through the hover delay; the machine enforces this so a pointermove racing a dismiss can't re-show it for a frame.
- **`phase === "closing"`** keeps the card rendered for the exit animation (`PREVIEW_TIMING.exitMs`); `hoveredCard` is non-null during it.
- **The machine is warm for `warmWindowMs` after a preview was visible**: hovers during that window show at `warmShowDelayMs` instead of the preference delay, so browsing a board feels fluid without making the first popup twitchy.
- **Enter/exit is a hero zoom from the hovered card's rect**: `CardPreview` feeds `--preview-shift-x/y` + `--preview-scale-from` (computed from `anchorRect` vs the final position) into the `preview-in`/`preview-out` keyframes in `index.css`. Keep the animation anchored — an in-place zoom reads as a blink.
- **Printed/rules view switches preserve anchor placement.** `CardPreview` and external `RulesCardPreviewLayer` use `computePreviewLayout` with the same placement, anchor/pointer, effective right viewport edge, orientation, and printed-side-panel reservation. Rules previews may shrink further to fit their controls; toggling the view retains the source anchor rather than recentering a sticky pointer preview.
- **The preview is pointer-transparent until the enter lands** (`entered`, timer-armed — not `animationend`, which never fires under `prefers-reduced-motion`). The hero zoom travels across the hovered sprite; an interactive preview crossing the cursor steals pointer events from the canvas and kills the sprite's hover state.
- **Card face chrome matches Pixi geometry**: corner radius is proportional (`CARD_RADIUS / CARD_W` of card size — shared constants in `game.constants.ts`) and equals card-glint's painted `MODERN_CORNER_RADIUS` (`faceCornerRadius` returns it for every modern face). `rulesCardRadius` derives from the same ratio, so the Manabrew mask, rings and foil match the Realistic view when flipping. Retro faces are painted rounder (0.058) by card-glint itself. Printed previews use the card image's own border; color-identity border chrome is reserved for the rules view. Don't reintroduce fixed `rounded-*` on the preview card.
- **Images are monotonic** (`PreviewImageStack` in `CardPreview`): pixels already shown are never removed until the replacement loads. Swapping an `<img>` src blanks it instantly — a naive URL swap (Scryfall faces resolving, low→high res, card switch) is the image flash.
- **Battlefield hover-out is `BoardScene`'s** (`scheduleHoverClear`, also fired on sprite `destroyed` — a removed sprite emits no `pointerleave`). Hover is also **re-asserted on every `pointermove` over any sprite** (force `setBattlefieldCardHovered` — not just the remembered card): a spurious `hoverEnd` (the preview firing enter/leave as it jumps positions during an instant switch) must not close a preview while the cursor sits on the card, and a `pointerenter` swallowed whole by the hand-hover gate (`hasActiveHover`, e.g. the fan grazed mid-sweep) leaves the scene with a stale hover belief that only raw pointer truth can repair — gating the re-assert on `hoveredCardId` is exactly what made a preview die permanently on the card you stopped on. The machine keeps the re-assert free — `hoverStart` early-returns when the same card **object** is already open, and a changed DTO object refreshes the open preview.
- **Zone changes follow authoritative snapshots.** Battlefield entries removed by a snapshot fade in place; the client does not synthesize flights toward destination zones. Seed positions and scales for battlefield arrivals and cross-region combat movement are canvas-global, converted through the root transform at region boundaries.

## Prompt routing

The engine sends a `Prompt` (from `@/protocol`) → `Game.tsx` builds a `PromptOverlaySpec` → `BoardOverlayCanvas` forwards it to the public `@/pixi/prompts/PromptLayer` orchestrator. `PromptLayer` owns lifecycle, keyboard handling, and the action cluster; `PromptModalLayer` renders modal and game-over surfaces; `PromptLayerBase` owns shared prompt/card/drag state and drawing primitives. The hierarchy switches on `prompt.input.type` and answers through `respond(<PromptOutput>)`. Modal prompts own the full overlay hit area; the action cluster reports only its rendered bounds. Modal surfaces lay out within `viewportRight` (the expanded `RightActionPanel`'s left edge, the same bound the previews use) while backdrops still cover the whole canvas. Non-prompt overlays such as zone viewer and ability picker remain React in `GameOverlays`.

Engine modals, including damage order, can minimize and reopen without clearing their pending choices. A collapsed damage-order prompt routes to `promptRequired`, not `noAction`, so its reopen control remains available. Reopening a modal prompt atomically closes any zone viewer; these are competing inspection surfaces, and retaining the zone lets the restore pointer reveal or reactivate it.

Combat-damage assignment follows the Foundations rules: blockers have no damage assignment order and may receive any split. Only assigning damage to the defender requires lethal assigned to every blocker; pointer controls, normalization, and keyboard confirmation must enforce the same constraint. The text-only damage dialog has no card-view or face-flip shortcut hint.

Card-bearing prompts use hand-style cards inline. `chooseCards`, `revealCards`, `reorder`, and `scry` all build those cards through `PromptModalLayer.createCardTile`; selection and drag/drop stay on the tile, not the rules face. Prompt tiles use the `GAME_CARD_SIZES.prompt` base dimensions, whose width and height are each scaled by `√0.7` so their area is exactly 70% of `GAME_CARD_SIZES.preview`. Source cards remain at the preview base size and are sized independently. Prompt tiles and source cards may shrink further only for viewport or orientation constraints; dense rows overlap, wrap, or scroll instead of inventing another card size. The action cluster is not a card-selection surface, so its compact source thumbnail uses `GAME_CARD_SIZES.battlefield`. New prompts use the persisted **Prompt default preview** preference and default to the realistic face. Hover or focus a prompt card before using the configured change-view and flip shortcuts; controls use compact icon buttons with tooltips, and landscape/split faces follow the same orientation semantics as hand cards.

`chooseCards` and `revealCards` split their cards into labeled zone sections (SIDEBOARD, HAND, …) only when the prompt cards come from two or more zones (`promptCardSections`). The zone comes from authoritative `CardDto.zone`, which both producers populate for known ordinary zones; outside-game paper cards and unrepresentable zones can omit it. A prompt with any card without a zone renders one unlabeled row. Do not derive the zone from `gameView`, because hidden library cards and outside-game cards both appear in no visible zone there.

Choose/reveal card prompts size to their card content, using a compact single-card minimum and a three-prompt-card panel cap for larger grids. Compact reveal prompts instead keep the height-fit prompt card size and lay every card out in one non-overlapping row that drag-pans horizontally (masked, clamped, grab cursor) when it overflows the viewport, so each card stays individually readable. Apply viewport and source-rail constraints before calculating columns; unused panel width must not push the source card away from sparse choices. Center every populated row from its actual card count so the left and right padding match, including a partially filled final row. Keep one `CARD_TILE_EDGE_INSET` above card-only rows so passive hover zoom remains inside the prompt body mask. Compact reveal rows with more cards than the viewport fit render a `first / total` progress readout under the row, gain release momentum on drag, and grow a GRID footer button that opens the shared card browser over the same set.

Prompt tiles and source previews reuse `HandCardControls` for printed/rules view changes and eligible face flips or landscape rotation. Controls and keyboard shortcuts share per-card state. Control presses stop before tile selection or dragging; hovered cards rise above overlapping neighbors so their controls remain reachable, while dragged cards retain the higher drag layer.

Prompt card wrappers add feedback and selection/drag behavior without taking input from embedded rules controls. The rules body owns touch presses and touch scrolling; mouse presses on it reach the outer card gestures, so hand and prompt cards drag from any point. Wheel input over a card in the modal body scrolls the modal; only the source card scrolls its own rules, through `PromptLayerBase` and `BoardOverlayCanvas`, respecting masks and modal ownership. Card feedback and scrolling request rendering through the existing callbacks rather than relying on another surface's ticker.

Every draggable prompt card lifts with a stronger `gameTheme.cardRing` outline and tilts slightly with horizontal pointer movement. Return scale, rotation, origin, and ring state during both successful and cancelled drag settlement; respect reduced-motion preferences.

Dice prompts use flat cached face and pip geometry with the player's color on the border. Arrange results in stable centered rows and start every displayed die together through short deterministic `@/pixi/effects/gsap` motion paths with per-die direction, distance, curvature, duration, and spin. Endpoints remain ordered even though the rolls vary; do not reintroduce shuffled placement, top-of-modal drops, particles, auras, glints, shadows, or decorative facets. Drive transient values from shared elapsed time and lock each result when its die lands. Reduced motion settles every die immediately.

Zone viewers always use the compact Pixi card grid; do not replace browse-only zones with the side inspector layout or autofocus the first card when the modal opens. Hover or keyboard focus slightly enlarges browse-only and unavailable cards without a glow; every hovered card remains eligible for the configured change-view shortcut regardless of action legality. Legal actionable cards instead receive the thin `gameTheme.cardRing` feedback without requiring a click first. Persistent selections use `gameTheme.cardSelection`. In actionable modes, legal playable or targetable cards use `CardSprite.setPlayableRing`, giving them the same thin, vibrant pulse as playable battlefield cards; hover and selection temporarily replace that pulse with their stronger static feedback. Wheel input over a card scrolls the zone grid, not the card's rules body. Keep every card at full opacity so zone contents remain readable; unavailable and pending cards communicate through cursor, hover-scale, and ring behavior instead of fading. Browse and cast activations close the zone after dispatching the card action so play-mode or payment prompts receive the full surface; target and cost selection keep it open across repeated choices. Target, cast, browse-action, and cost modes activate legal cards directly; browse-only card clicks do nothing, and manual moves retain the explicit footer confirmation. Keep final card positions stable and reserve persistent checks for actual selection.

Scry keeps prompt-size cards in the source pool, horizontally pannable on desktop, while any prompt source card remains preview-size in its separate rail. Once placed, a card is rebuilt as a natural `CardSprite(card, "zone")` at `GAME_CARD_SIZES.battlefield`; compact landscape prompts place the title and guidance in one row, omit desktop-only shortcut hints, spend the reclaimed header and footer height on larger pool cards, and fit destination cards, wells, icons and stack depth independently of readable labels. A pool card uses GSAP to shrink to half scale as soon as its drag clears the movement threshold. A valid release hands the half-size visual directly to the destination rebuild, which moves and finishes minimizing it in one continuous animation with the top card centered in the well; an invalid drop restores prompt scale, and returning a card to the pool expands it. Only the top destination card remains interactive and draggable, while selected feedback stays visible at battlefield scale. Drag targets highlight the full rounded zone border, including the source pool; highlight graphics remain pointer-transparent and clear when the drag leaves or ends. Desktop keeps full `cardWidth + PROMPT_CARD_GAP` slots inside a masked, wheel-pannable pool and shows a thumb only when the row overflows. Compact touch prompts overlap pool cards enough to keep the complete row visible without scrolling. The drop preview slot clamps into the visible pool, and desktop pool offset survives rebuilds but resets with the prompt.

Choice-search focus is independent of the query text. Show the themed focus border and a typing caret while focused, preserve focus across filter-result rebuilds, and use a steady caret under reduced motion. Keep search above the clipped, touch- and wheel-scrollable choice list and selection status and confirmation below it. If that chrome would leave less than one choice row, collapse the header and combine search and confirmation in a top toolbar, with selection totals in the confirm control. Keep rows unscaled and source cards visible in the external rail at the shared preview dimensions. Restore the full header and footer when the viewport grows.

Searchable choice and card prompts share `choiceSearchInput`, a native search input focused synchronously from the Pixi search field. Prevent the search press's browser default so a following mouse-down cannot blur the input. Preserve it across result rebuilds and release it when the prompt hides, changes, or is destroyed. Choice-list touch scrolling applies to both presentations because tablets use the desktop scene. Native `pointercancel` owns gesture cancellation because Pixi's event system does not subscribe to it; remove that listener with its panel. Prompt viewport sizing follows `visualViewport` resize so the keyboard leaves confirmation reachable.

Desktop modal prompt wheel scrolling preserves pixel deltas, converts line/page deltas, scales the result, and clamps only extreme steps. Do not replace it with a fixed step per wheel event because trackpads emit many small events. Touch prompts reflow choices, cards, source rails and ordering surfaces before scrolling overflowing content. Keep UI text unscaled, headers and confirmation reachable, and card fitting independent. Footers wrap rather than shrinking their controls. Enter and Space activate the available primary footer action. A focused choice-search field keeps Space as text input instead.

`useKeybindings` capture listeners stop propagation only when a handler does not return `false`. The global `pass-priority` handler must return `false` when it has no action for the current prompt so Space reaches `PromptLayer`; swallowing that event breaks modal primary actions such as Reveal's Continue.

`reorder` keeps every card in one **Resolution order** strip whose height hugs the card row and its controls; size the modal to that strip plus its header and confirmation footer rather than the viewport. The leftmost card resolves first, and horizontal drop position chooses the insertion index. While dragging, close the source gap and glide neighboring cards aside to expose the pending destination before release; do not mutate the submitted order until drop. Initialize the strip from the engine-provided order, center the earlier/later controls beneath each card, and use `gameTheme.cardRing` for their hover/focus accent. After either a drag or button move, preserve each card's previous global position so displaced cards glide into their new slots without replaying a scale pulse. Inset both the strip and its cards far enough that rank badges, rings, and rounded borders remain inside the modal mask.

Center each prompt-and-source cluster on the viewport. `PromptLayerBase.promptSourceCardDisplayDimensions()` uses the same `computePreviewCardDimensions()` calculation as battlefield long-press previews, including orientation, safe-area-adjusted viewport width, and viewport height. Every prompt must render its source card at those exact dimensions; prompt layout receives only the remaining width after `SOURCE_CARD_GAP` and must never shrink, scale, or re-fit the source independently. Compact landscape prompts use the full inset viewport height, place the prompt in the left rectangle, and vertically center the source in the right rectangle. Live prompts use `currentPrompt.sourceCard` directly; fixtures may fall back to `sourceDeckCard`. Apply `currentPrompt.sourceAbilityText` through `CardSprite.setHandRulesHighlight` so the resolving rules entry receives the same pulse used by stack rules cards.

`PromptModalPreview` must portal the overlay canvas directly to `document.body`. `RightActionPanel` uses `backdrop-filter`, which creates a containing block for fixed descendants; an inline full-screen preview canvas is then constrained to the panel while retaining a viewport-sized Pixi coordinate system, leaving the prompt off-screen and capturing input. Route the preview through `MobileBoardOverlayCanvas` when `useIsMobileGame()` is true and `DesktopBoardOverlayCanvas` otherwise; forcing the desktop renderer makes compact scry and card prompts use desktop sizing.

Board and overlay stage hit tests must reject input beneath the top modal; the owning prompt canvas retains pointer and keyboard input. Document-level board hover reconciliation must also yield to the live overlay hit test.

The open Dev tab sits above the gameplay overlay but below portaled full-screen prompt previews. Touch routing must respect the topmost DOM element before replaying a touch onto the canvas. Scry's landscape, double-sided, and mixed-layout dev choices load real card metadata through the shared Scryfall store and reuse the preview scenario catalog.

## Theme

This subtree is the most color-heavy in the app. **No hex / rgba / palette tailwind.** Add a semantic key to `GameThemeColors` (in `src/themes/gameTheme.ts`), wire it in `buildGameColors()` (in `src/themes/buildGameColors.ts`), regenerate the Tailwind `@theme` block with `node scripts/generate-theme-css.mjs --write`, then use the generated token utility (`bg-targeting-hostile`, `text-counter-p1p1`, `ring-card-ring`, `bg-pt-buffed`, …). See `docs/agents/UI_THEME_RULES.md`.

Gameplay chrome follows app light/dark mode; do not force a dark scope. Light phase strips and loading-card placeholders inherit neutral app surfaces unless a shared personal game override is set. Pair phase/placeholder ink with the resolved fill and prompt text with its app surface. Keep board artwork, native card inks, and rules-significant hues independent of app mode. Use `cardRing` for battlefield focus/availability and `cardSelection` for selected cards, not light-mode app-primary ink on a dark table.

Use `PromptButton.action` for gameplay buttons and `variant` for app actions so the corresponding foreground is applied. Pass and priority actions use the app `primary` and `primary-foreground` tokens; full priority controls retain their shared primary surface in both horizontal and stacked layouts. Attack and defense keep their distinct game prompt roles. Arrows, pointer glows, target rings, casting previews, and zone actions share only `targeting.hostile` and `targeting.friendly`. Seat colors remain identity marks. `cardRing` means availability or hover, `cardSelection` means persistent selection, and `zone.*`, `connection.disconnected`, and `cardStatus.summoningSick` are independent roles. The `/card-mock` gameplay fixtures render through the real board overlay using local state and the shared pure dialog/prompt builders.
