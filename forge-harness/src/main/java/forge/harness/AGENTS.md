# forge-harness — package boundaries

Java side of the cross-engine work. One CLI entry, three internal packages with one-directional dependencies.

```
forge.harness            Main            CLI launcher / dispatcher (one-shot, --server, --interactive-server)
forge.harness.common     generic harness shared by parity AND host
forge.harness.parity     deterministic full-game parity runner
forge.harness.host       interactive self-hosted-node engine surface
```

Dependency rule (do not violate): `parity → common`, `host → common`, `Main → {common, parity, host}`. **`common` never imports `parity` or `host`. `parity` and `host` never import each other.** If a `common` class reaches for a `parity`/`host` type, it is misfiled — move it, don't add the back-edge.

## What goes where

- **common** — anything used by both engines: RNG (`CountingRandom`), logging (`DecisionLog`, `ParityLog`), snapshot base (`SnapshotExtractor`), GUI bootstrap (`HeadlessGuiBase`), deterministic ordering / id mapping / reset (`ParityOrder`, `ParityCardMap`, `ForgeEngineReset`), the shared decision/cost/play plumbing (`ActionSpace`, `ChoiceSpace`, `CombatChoiceSpace`, `AutoPay`, `HarnessCostPlumbing`, `HarnessPlayPlumbing`, `HarnessPlayHooks`), and the prompt acceptance-rule facade (`EngineHandler`). `EngineHandler` is the one entrypoint for Forge GUI/controller legality: per prompt it returns the legal choice set (so a caller only offers valid picks) and post-validates the submitted answer for whole-answer constraints a per-option set can't express (e.g. `CombatUtil.validateBlocks`). Heavy mechanics stay in `ActionSpace`/`ChoiceSpace`/`CombatChoiceSpace`; `EngineHandler` unifies them.
- **parity** — `DeterministicController`, `DeterministicLobbyPlayer`, `PresetDecks`.
- **host** — `ManaBrewEngineAdapter` (the in-process facade Rust j4rs talks to), `ManaBrewInteractiveSession`, `ManaBrewInteractiveController`, `ManaBrewInteractiveLobbyPlayer`, `InteractiveSnapshotExtractor`, `PriorityFastForward` (`reachedTarget`/`canSkip`: skips priority windows with no roundtrip while the player has a standing **held** pass-until whose target is a `(player, phase)` slot — a bare phase can't tell "my end" from an opponent's. The controller holds the declaration across windows and clears it on reaching the target, on casting, when the target player has lost — their slot would never arrive — when the holder begins an extra turn while the target points at another player (the client computed the slot assuming normal turn order, so honoring it would silently fast-forward the holder's own extra turn), or when the phase sequence steps backward within a turn (`invalidatedByExtraPhase`: an inserted extra phase — Moraug, Aggravated Assault — breaks the linear phase model the client computed the target from; without the clear, the hold swallows the repeated combat, empty attacker declaration included); mirrors `manabrew-engine` `priority.rs` and the `AdvanceTurn` clear in `game_loop/phase_handler.rs` — the extra-phase clear is NOT yet mirrored in the Rust engine). `PriorityFastForward` also carries the exhaust-stack pass (`stackIds`/`exhaustEnded`, host-only — the Rust engine ignores the protocol's `exhaustStack` flag for now): the controller snapshots the stack-instance ids at declaration and silently passes priority until the stack empties, stopping early as soon as any new object — spell, activated ability, or trigger — enters the stack, so the holder can respond to it.

### Host payability probes must stay silent

`ManaBrewInteractiveController` sets `probingPayability` while engine code runs feasibility tests (`ActionSpace.getPossibleActions` → `ComputerUtilMana.canPayManaCost`, and the `ComputerUtilCost.canPayCost` pre-checks). These test paths call regular `PlayerController` choosers (`chooseCardsForConvokeOrImprovise`, `chooseCardsToDelve`, `choosePermanentsToSacrifice` via offering/emerge, `choosePlayerToAssistPayment`) — in native Forge only the AI ever hits them. Any chooser reachable from `CostAdjustment`/`ComputerUtilMana` must check the flag and answer silently (maximally permissive) instead of round-tripping to the UI. The real prompt happens once, in `payManaCost`, via `CostAdjustment.adjust(..., test=false, ...)` mirroring `HumanPlay.payManaCost` (taps convoked creatures, collects delve cards; `handleOfferingConvokeAndDelve` mirrors the HumanPlay helper). `DeterministicController` mirrors the same `probingPayability` flag around `ActionSpace.getPossibleActions` so its `chooseCardsForConvokeOrImprovise` returns the optimistic greedy estimate during action-space probing and declines (empty) during real payment.

### Phyrexian life payment is host-only in the action space

`ComputerUtilMana.canPayManaCost` pays `{B/P}`-style pips greedily with real sources and never backtracks, so a cost like `{4}{B/P}{B/P}{B/P}` with 4 Swamps tests as unpayable even though paying the pips with life would work (issue #378). The interactive host passes `lifePaymentFallback=true` into `ActionSpace.getPossibleActions` and `HarnessPlayPlumbing`, which retries via `ActionSpace.canPayManaCostWithLifeFallback`: it searches every phyrexian / `PayLifeInsteadOf:B` shard state and re-runs Forge's mana check, excluding reserved sacrifices from the mana sources. `PayLifeInsteadOf:B` eligibility mirrors Forge's human input through `ManaCostBeingPaid.hasAnyKind`, so color-restricted X is not life-payable. Human legality never consults the AI-only `AIPhyrexianPayment` preference. `DeterministicController` passes `false` **on purpose**: the Rust engine's action space (`can_pay_spell_mana_cost_for_action_space`) has the same greedy no-backtracking behavior, and parity requires mirroring it. Widening the parity path without the matching `manabrew-engine` change breaks `yarn parity phyrexian_mana`. The `pay_mana_cost` prompt advertises the option as a `PaymentAction::PayLife` entry (set from the controller's `canPayLife`), answered by echoing its id through `PayManaCostOutput::Act`; each payment chooses a specific life-payable shard that preserves a valid remaining payment plan when possible.

### The action-space payability probe

Forge does **no** mana-payability prediction for humans: `Card.getAllPossibleAbilities` filters on `sa.canPlay(true)`, `CostPartMana.canPay()` is permissive, and the GUI simply offers unaffordable actions and lets the mana input be cancelled. The harness needs a real action space for the protocol, so it predicts — but `ComputerUtilMana` lives in **forge-ai** and is conservative by construction, which is where every divergence comes from.

`ActionSpace.probeManaCost` is a mirror of `ComputerUtilMana.calculateManaCost` in test mode minus one line: `sa.setMaxWaterbend(null)`, which the core applies whenever `payer.getController().isAI()` is false to stop native Forge prompting a human mid-prediction. Neither harness controller overrides `isAI()`, and the core guard cannot see `probingPayability`, which already makes every chooser answer silently. Zeroing it makes the following `CostAdjustment.adjust(manaCost, …, test=true, …)` skip `adjustCostByWaterbend` entirely, so a cost payable by tapping artifacts and creatures tests as unpayable and the action never reaches the client. Keeping the value lets that single pass account for waterbend, convoke, improvise, delve, offering and emerge at once.

**Do not add per-mechanic fallbacks to this class.** The next mechanic Forge's AI predictor under-reports belongs in `probeManaCost`, not in a new `canPayCostWithX` helper — and never wrap a generic cost check in a mechanic-named one. `probeManaCost` feeds `canPayManaCostWithLifeFallback`, the host-only entrypoint; the parity branch of `getPossibleActions` still calls `ComputerUtilMana.canPayManaCost(sa, …)` directly and is deliberately unchanged. Phyrexian stays a separate fallback because it is a defect inside `payManaCost`'s greedy shard spend, not the adjust pass. Effect costs (`UnlessCost$`, prevent-effect, roll costs) go through `ActionSpace.canPayCost`, which mirrors the `effect=true` path of `ComputerUtilCost.canPayCost` — mana feasibility plus `CostPayment.canPayAdditionalCosts`; the AI-only heuristics there sit behind `!effect` — over the same `probeManaCost`.

The whole scan re-runs on every priority prompt and on every mana undo, so the order of the guards in `getPossibleActions` is load-bearing, not cosmetic (#684). Keep `hasValidTargets` behind the payability guards: it calls `TargetRestrictions.getAllCandidates`, which walks every card in the target zones, and late in a Commander game most candidates are unpayable. For the same reason `canPayManaCostWithLifeFallback` returns early unless the cost actually has a shard `canPayShardWithLife` accepts — the recursion's first `canPayManaOnly` forces `AIPhyrexianPayment=Never`, which is strictly stricter than the check that already failed, so without such a shard the second probe is a foregone `false`. The LKI copy behind `checkRestrictions` is memoised per host card for one pass; it depends only on the card and the stack zone, and a card with several castable faces or alternative costs would otherwise clone itself once per ability.

### Convoke / Improvise in payment

`chooseCardsForConvokeOrImprovise` declines the upfront cost reduction outside payability probes (both controllers). Convoke/improvise is then resolved at payment time: interactively in `ManaBrewInteractiveController.payManaInteractively` (`payConvoke`/`convokePaymentSources`), and automatically in `AutoPay.payConvokeImprovise` for the committing auto-pay path (only the parity runner routes through it; the host's auto button floats mana via `AutoPay.floatManaForCost` and leaves convoke/improvise taps to explicit prompt actions). Both tap the chosen creatures/artifacts, record `sa.addTappedForConvoke`, fire the `TapAll` trigger, and reduce the cost via `ManaCostBeingPaid.payManaViaConvoke`. **Parity caveat:** the Rust engine's auto-pay does not yet tap convoke/improvise sources, so `yarn parity` diverges on convoke/improvise spells until `manabrew-engine`'s auto-pay is mirrored.

### Waterbend in payment is a typed resource, not a mana ability

Convoke/improvise sources are emitted as `activateManaAbility` (`tap:<cardId>`), which leaves the client unable to tell a land tap from a cost-reduction tap. Waterbend does **not** reuse that: it emits `useResource` / `releaseResource` with `PaymentResourceKind.WATERBEND` (ids `waterbend:<cardId>` / `unwaterbend:<cardId>`), the same shape delve uses, so the UI can label and count it. Adding a `PaymentResourceKind` variant means the usual three regens — `yarn gen:types`, `yarn build:harness`, `yarn gen:protocol-docs`.

`payManaInteractively` keeps a `sessionWaterbend` shard map and a `waterbentCards` collection alongside the convoke ones. `waterbendCandidates` filters on `CardPredicates.CAN_TAP` + artifact-or-creature, mirroring `adjustCostByConvokeOrImprovise` exactly, rather than the plain `isTapped()` check `convokePaymentSources` uses. The two agree for every printed card (no card scripts an `R:Event$ Tap` replacement), so this is parity hygiene, not a live fix — but it keeps the payment surface consistent with `ActionSpace.applyWaterbendReduction`, which already uses `CAN_TAP`. `waterbendPaymentSources` offers those while `waterbentCards` is under `sa.getMaxWaterbend()` (set by then via `CostPayment` → `CostAdjustment.adjust`) and generic remains, and keeps already-waterbent cards in the list so they can be released — mirroring `delvePaymentSources`. It does not require `sa.isSpell()`: activated-ability waterbend (Watery Grasp, Katara) is the common case. An X waterbend budget (`Waterbend<X>` via RaiseCost, e.g. Crashing Wave) needs X **before targeting**, but the announce step reads the raw cost — the Waterbend<X> part only exists after `CostAdjustment.adjust` merges the static. `HarnessPlayPlumbing.announceAdjustedCostX` announces X from the adjusted cost's `getMaxWaterbend()` exactly as a scripted `Announce$ X` would (Waterbender's Restoration carries one; Crashing Wave does not — upstream native Forge is broken for this card: X resolves to 0 and targeting locks at "up to 0"). Parity note: this consumes an announce decision the Rust engine does not mirror; irrelevant while Rust lacks waterbend entirely.

`payWaterbend` pays a colorless shard via `payManaViaConvoke` — `InputSelectCardsForConvokeOrImprovise` takes the `if (artifacts)` branch for waterbend, so it never prompts for a colour even on creatures — and never calls `sa.addTappedForConvoke`, matching `adjustCostByConvokeOrImprovise`'s `creatures && !artifacts` guard; `unwaterbend` refunds the recorded shard and untaps. The auto button fills but never commits: it floats real mana via `AutoPay.floatManaForCost`, then `autoWaterbend` taps waterbend sources only for generic the pool cannot cover (guarded by `poolCanCover`, so a board is never tapped when lands suffice). The session re-prompts with the taps releasable and Confirm lit — the commit is always the player's Confirm click, and no manual tap commits either (the convoke/waterbend `isPaid` returns were removed).

### Delve in payment

Delve follows the same shape on the interactive (host) side only. `chooseCardsToDelve` declines the upfront reduction outside payability probes (returns `CardCollection.EMPTY`); the cost stays full into `payManaInteractively`, which exposes the activator's graveyard via `delvePaymentSources` (gated on the host's `DELVE` keyword and remaining generic). Picking a card (`delve` action → `payDelve`) defers it into the same `cardsToDelve` collection `CostAdjustment` would have filled — `decreaseGenericMana(1)` per card, no mid-session exile — and `undelve` reverses it (`increaseGenericMana`). The actual exile happens once, at the end, in `handleOfferingConvokeAndDelve`; cancel rolls back via the mana-payment snapshot, so there is no per-card un-exile. The host auto button greedily fills remaining generic from the graveyard (`autoDelve`) and then floats mana via `AutoPay.floatManaForCost` — it never commits; the loop re-prompts with `canConfirmFromPool` and the user confirms from the pool (`Pay` with `auto=false`). The `pay_mana_cost` prompt presents every payment option as one `PaymentAction` in a single `actions` list — mana abilities (`activateManaAbility`, id `tap:<cardId>:<idx>[:<color>]`), untap (`undoMana`, id `untap:<cardId>`), and delve resources (`useResource`/`releaseResource`). **The protocol drives; the client only renders the actions and echoes an `id` back — it holds no payment state and synthesizes no ids.** `publishManaPaymentPrompt` reads the live `cardsToDelve` set and emits each graveyard source as `useResource` (id `delve:<cardId>`) when not yet delved or `releaseResource` (id `undelve:<cardId>`) when it is, re-prompting after each toggle. The UI derives the "delved" highlight from `type === "releaseResource"` and answers `PayManaCostOutput::Act { actionId }` with the offered id (or `Pay`/`Cancel`) — never building a `delve:`/`undelve:` id itself. The distinct resource actions are earned by the separate render surface: delve lives in the graveyard zone-viewer, not the battlefield-tap surface. `ManabrewProtocolAdapter.parseActionId` decodes the id back into the internal `kind` action (`delve`/`undelve`/`tap_land`/`untap_land`). `DeterministicController` (parity) is unchanged — it still resolves delve upfront via `CostAdjustment`. The Rust engine backend does not yet offer in-payment delve, so this is host-only.

### Concede (the `Directive` channel)

Concede mirrors native Forge's out-of-band contract: `player.concede()` sets the outcome (so `hasLost()` is true immediately and `PhaseHandler` routes around the lost player), and the loss is processed by the engine's next state-based-actions pass. **Never call `checkGameOverCondition()` from inside an await** — `onPlayerLost` (CR 800.4 cleanup, reveals, lose triggers) can consult controllers, and a nested prompt published mid-await clobbers the open prompt (`latestPromptJson`) which `java_backend`'s prompt-id dedup never re-forwards: permanent deadlock. The wire carries it as a directive, never a prompt answer: `java_backend.rs` submits `{"type":"directive","directive":{"type":"concede"},"player":N}` (the seat index travels with the directive — the drain loop covers every seat, so a concede can arrive while a different player's prompt is open). `ManabrewProtocolAdapter.translateDirective` maps it to `{"kind":"concede","player":N}`, and the session's single take-core (`ManaBrewInteractiveSession.takeAction`) executes the concede **on the game thread** for the named seat. If the conceded seat is the prompted player (or the concession ended the game) the action becomes a synthetic `{"kind":"pass"}` — every await site already treats pass as its safe default — otherwise the take-core keeps waiting for the prompted player's real answer. The take-core never parks indefinitely: it polls with a 1s deadline and returns a synthetic pass once the session is closed or the game is over, so an aborted session's game thread always unwinds through the awaits' pass defaults (`close()`'s single unblocking pass is not enough on its own — the thread can re-await while unwinding). Never bypass `takeAction()` with a raw `actions.take()`.

## Typed prompt emission (compile-time protocol check)

The host **does not hand-build prompt JSON.** `manabrew-protocol` (Rust) is the source of truth: `scripts/gen-harness-prompts.mjs` reads its generated TS bindings and emits one Java class per prompt input + referenced shared type into `forge-harness/src/main/java/forge/harness/protocol/` (package `forge.harness.protocol.*`), each baking in its own `type` discriminator. `scripts/harness.mjs` regenerates them before every build. The package is generated, gitignored (`forge-harness/.gitignore`), and lives under the standard `src/main/java` root on purpose: m2e/JDTLS has no build-helper connector, so an out-of-tree generated-sources dir never lands on the IDE classpath. Never hand-edit anything in this package.

`ManaBrewInteractiveSession` builds each prompt as a typed object (`new ChooseCardsInput(presentation(...), richCards(...), min, max)`) and `publishAgentPrompt(Object)` serializes it with Gson (camelCase fields, `@SerializedName` enums, nulls omitted). So a protocol change the harness no longer matches — a removed/renamed/retyped field, a dropped prompt — is a **compile error here**, not the silent runtime drift that previously killed `java_backend`'s deserialize (the `chooseType`/`chooseCardName`/`divideAmount` class of bug; `divideAmount` is now `chooseNumber`-per-target). `InteractiveSnapshotExtractor.cardDto` and state cards (`battlefield`, zone lists) are typed `CardDto` too. **Do not reintroduce raw `JsonObject` prompt building** — build the generated class. The compiler is the guard.

Snapshots are **per-viewer**: `getSnapshot` takes a `viewer` seat index (`-1` = spectator) and `InteractiveSnapshotExtractor` gates every card on Forge's visibility oracle — `CardView.canBeShownTo(viewer)` (hands controller-only, library hidden unless `MayLookAt`, face-down exile hidden unless the viewer may look — foretell grants the owner that right) and `canFaceDownBeShownTo`/controller for battlefield morph faces (redacted DTO, never dropped from the list, since the shell is public). Hidden hand/library cards are elided to the zone `count`; hidden exile cards stay as `{visibility:"hidden", id}` entries so clients render an anonymous face-down card. A serialized face-down card carries its real paper identity — visibility is the caller's decision, `redact()` blanks what a viewer may not see. Do not serialize a card the viewer can't see.

## Boundary API discipline

`common` types are `public` only where genuinely consumed across a package boundary. `HarnessCostPlumbing` / `HarnessPlayPlumbing` / `AutoPay` expose **only** the constructor + methods the two controllers call (`payWithControllerDecision`, `isSpellPaymentContext`, `currentReservedSacrifices`, `playNoStack`, `handlePlayingSpellAbility`, `prepareSingleSa`, `orderAndPlaySimultaneousSa`, `playSaFromPlayEffect`, `payManaCost(WithTrace)`, `manaSources`, `floatManaFromSource`, `floatManaForCost`, `PayManaCostResult.paid/steps`); everything else stays package-private. When adding a member, keep it package-private unless a controller in `parity`/`host` needs it — don't widen the surface by default.

## External references (keep in sync)

- `forge.harness.Main` is the jar `mainClass` (pom) and is invoked by parity and self-hosted-node (CLI flags). Keep `Main` in the root package.
- `forge.harness.host.ManaBrewEngineAdapter` is loaded by class name in `src-tauri/src/engine_backend/java_backend.rs` (`create_instance`). Moving/renaming it means updating that string.

## Build / verify

Jar is produced by `node scripts/harness.mjs ensure` (or `yarn build:harness`). Never call Maven yourself: `forge.harness.protocol.*` is generated and gitignored, so a bare `mvn` compiles against whatever stale sources happen to be on disk — or none at all on a fresh clone. `build-checks.yml`'s `harness-entrypoint` job rejects any workflow or Dockerfile that does. For a fast compile-only check against an existing fat jar:

```
javac -d /tmp/out -cp target/forge-harness-jar-with-dependencies.jar $(find src/main/java -name '*.java')
```

**After a `forge` submodule bump, do a _clean_ rebuild** (`yarn build:harness --clean`). `ensure`/`package` are incremental and key off source mtime, not the classpath — so a Forge change recompiles `forge/` but reuses the harness `.class` files compiled against the **old** Forge, silently shipping a broken jar (missing newer card enums like `CardSplitType.Prepare`, or synthetic `switch`-map classes like `SnapshotExtractor$1` → deck-load failures or a runtime `NoClassDefFoundError`). A Forge API change may also require updating the `PlayerController` overrides in `host/ManaBrewInteractiveController` + `parity/DeterministicController` (and call sites in `common/HarnessPlayPlumbing`) before it compiles. Keep the submodule pinned to the recorded gitlink with `git submodule update --init forge`; only `--remote` advances it. Build with JDK 17+ — that is Forge's enforcer floor, and 21 and 25 both build the full reactor; there is no upper bound at 21, though a very new JDK can still break Forge's build as 26 did.
