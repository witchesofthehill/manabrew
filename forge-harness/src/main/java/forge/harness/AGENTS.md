# forge-harness — package boundaries

Java side of the cross-engine work. One CLI entry, three internal packages with one-directional dependencies.

```
forge.harness            Main            CLI launcher / dispatcher (one-shot, --server, --interactive-server)
forge.harness.common     generic harness shared by parity AND host
forge.harness.parity     deterministic full-game parity runner
forge.harness.host       interactive self-hosted-node engine surface
```

Dependency rule (do not violate): `parity → common`, `host → common`, `Main → {common, parity, host}`. **`common` never imports `parity` or `host`. `parity` and `host` never import each other.** If a `common` class reaches for a `parity`/`host` type, it is misfiled — move it, don't add the back-edge.

## What goes where

- **common** — anything used by both engines: RNG (`CountingRandom`), logging (`DecisionLog`, `ParityLog`), snapshot base (`SnapshotExtractor`), GUI bootstrap (`HeadlessGuiBase`), deterministic ordering / id mapping / reset (`ParityOrder`, `ParityCardMap`, `ForgeEngineReset`), the shared decision/cost/play plumbing (`ActionSpace`, `ChoiceSpace`, `CombatChoiceSpace`, `AutoPay`, `HarnessCostPlumbing`, `HarnessPlayPlumbing`, `HarnessPlayHooks`), and the prompt acceptance-rule facade (`EngineHandler`). `EngineHandler` is the one entrypoint for Forge GUI/controller legality: per prompt it returns the legal choice set (so a caller only offers valid picks) and post-validates the submitted answer for whole-answer constraints a per-option set can't express (e.g. `CombatUtil.validateBlocks`). Heavy mechanics stay in `ActionSpace`/`ChoiceSpace`/`CombatChoiceSpace`; `EngineHandler` unifies them.
- **parity** — `DeterministicController`, `DeterministicLobbyPlayer`, `PresetDecks`.
- **host** — `ManaBrewEngineAdapter` (the in-process facade Rust j4rs talks to), `ManaBrewInteractiveSession`, `ManaBrewInteractiveController`, `ManaBrewInteractiveLobbyPlayer`, `InteractiveSnapshotExtractor`, `GameCheckpoint` (journal-based reconstruction of a pending decision), `PriorityFastForward` (`reachedTarget`/`canSkip`: skips priority windows with no roundtrip while the player has a standing **held** pass-until whose target is a `(player, phase)` slot — a bare phase can't tell "my end" from an opponent's. The controller holds the declaration across windows and clears it on reaching the target, on casting, when the target player has lost — their slot would never arrive — when the holder begins an extra turn while the target points at another player (the client computed the slot assuming normal turn order, so honoring it would silently fast-forward the holder's own extra turn), or when the phase sequence steps backward within a turn (`invalidatedByExtraPhase`: an inserted extra phase — Moraug, Aggravated Assault — breaks the linear phase model the client computed the target from; without the clear, the hold swallows the repeated combat, empty attacker declaration included); mirrors `manabrew-engine` `priority.rs` and the `AdvanceTurn` clear in `game_loop/phase_handler.rs` — the extra-phase clear is NOT yet mirrored in the Rust engine). `PriorityFastForward` also carries the exhaust-stack pass (`stackIds`/`exhaustEnded`, host-only — the Rust engine ignores the protocol's `exhaustStack` flag for now): the controller snapshots the stack-instance ids at declaration and silently passes priority until the stack empties, stopping early as soon as any new object — spell, activated ability, or trigger — enters the stack, so the holder can respond to it.

### Replay snapshots

`GameCheckpoint` reconstructs pending decisions from a journal; `DecisionHistory` retains interactive rewind history. See `docs/DECISION_REPLAY.md` for isolation, delivery and verification contracts.

RPCs read immutable seat views published on the game thread before prompts, revisions and game over. Never traverse live Forge zones from RPC threads. During replay, defer UI views and checkpoint rows until the verified destination, but retain per-input verification and remembered-hand updates.

### Host payability probes must stay silent

`ManaBrewInteractiveController` sets `probingPayability` while engine code runs feasibility tests (`ActionSpace.getPossibleActions` → `ComputerUtilMana.canPayManaCost`, and the `ComputerUtilCost.canPayCost` pre-checks). These test paths call regular `PlayerController` choosers (`chooseCardsForConvokeOrImprovise`, `chooseCardsToDelve`, `choosePermanentsToSacrifice` via offering/emerge, `choosePlayerToAssistPayment`) — in native Forge only the AI ever hits them. Any chooser reachable from `CostAdjustment`/`ComputerUtilMana` must check the flag and answer silently (maximally permissive) instead of round-tripping to the UI. The real prompt happens once, in `payManaCost`, via `CostAdjustment.adjust(..., test=false, ...)` mirroring `HumanPlay.payManaCost` (taps convoked creatures, collects delve cards; `handleOfferingConvokeAndDelve` mirrors the HumanPlay helper). `DeterministicController` mirrors the same `probingPayability` flag around `ActionSpace.getPossibleActions` so its `chooseCardsForConvokeOrImprovise` returns the optimistic greedy estimate during action-space probing and declines (empty) during real payment.

### Phyrexian life payment is host-only in the action space

`ComputerUtilMana.canPayManaCost` pays `{B/P}`-style pips greedily with real sources and never backtracks, so a cost like `{4}{B/P}{B/P}{B/P}` with 4 Swamps tests as unpayable even though paying the pips with life would work (issue #378). The interactive host passes `lifePaymentFallback=true` into `ActionSpace.getPossibleActions` and `HarnessPlayPlumbing`, which retries via `ActionSpace.canPayManaCostWithLifeFallback`: it searches every phyrexian / `PayLifeInsteadOf:B` shard state and re-runs Forge's mana check, excluding reserved sacrifices from the mana sources. `PayLifeInsteadOf:B` eligibility mirrors Forge's human input through `ManaCostBeingPaid.hasAnyKind`, so color-restricted X is not life-payable. Human legality never consults the AI-only `AIPhyrexianPayment` preference. `DeterministicController` passes `false` **on purpose**: the Rust engine's action space (`can_pay_spell_mana_cost_for_action_space`) has the same greedy no-backtracking behavior, and parity requires mirroring it. Widening the parity path without the matching `manabrew-engine` change breaks `yarn parity phyrexian_mana`. The `pay_mana_cost` prompt advertises the option as a `PaymentAction::PayLife` entry (set from the controller's `canPayLife`), answered by echoing its id through `PayManaCostOutput::Act`; each payment chooses a specific life-payable shard that preserves a valid remaining payment plan when possible.

### The action-space payability probe

Forge does **no** mana-payability prediction for humans: `Card.getAllPossibleAbilities` filters on `sa.canPlay(true)`, `CostPartMana.canPay()` is permissive, and the GUI simply offers unaffordable actions and lets the mana input be cancelled. The harness needs a real action space for the protocol, so it predicts — but `ComputerUtilMana` lives in **forge-ai** and is conservative by construction, which is where every divergence comes from.

`ActionSpace.probeManaCost` is a mirror of `ComputerUtilMana.calculateManaCost` in test mode minus one line: `sa.setMaxWaterbend(null)`, which the core applies whenever `payer.getController().isAI()` is false to stop native Forge prompting a human mid-prediction. Neither harness controller overrides `isAI()`, and the core guard cannot see `probingPayability`, which already makes every chooser answer silently. Zeroing it makes the following `CostAdjustment.adjust(manaCost, …, test=true, …)` skip `adjustCostByWaterbend` entirely, so a cost payable by tapping artifacts and creatures tests as unpayable and the action never reaches the client. Keeping the value lets that single pass account for waterbend, convoke, improvise, delve, offering and emerge at once.

**Keep payability probes general and bounded.** `probeManaCost` handles Forge cost adjustments such as waterbend, convoke, improvise, delve, offering, and emerge; the host-only `canPayManaCostWithLifeFallback` retries phyrexian/life-payable shards. When a cost depends on announced `X` or chosen targets, `canPayManaWithAnnouncedX` and `canPayManaWithTargets` try legal values/target sets before the action is omitted. Targets matter for `ValidTarget$` reduce/raise statics and for `Relative$` reduce statics, whose amount SVar can read the SA's targets (Not of This World). A targeting SA with more than one target is offered without a search because the subset enumeration is exponential; payment rejects it and `rollbackAbility` restores the card. An SA whose `ValidTgts$` compares against an X it still has to announce (`cmcEQX` with `Count$xPaid`: Lazotep Quarry, Bronzebeak Foragers) skips `hasValidTargets`, because the probe sees that X as 0. Forge announces X before `setupTargets`; a player with no legal target for the chosen X cancels at targeting, and `handlePlayingSpellAbility` clears the announced X so the next scan and activation start fresh. Targets that do not read X keep the check (Heat Ray with no creature is not offered). `ActionSpaceTest` locks both cases. Preserve the fast ordinary-cost path: the whole scan reruns on every priority prompt. The parity branch still calls `ComputerUtilMana.canPayManaCost(sa, …)` directly. Effect costs (`UnlessCost$`, prevent-effect, roll costs) use `ActionSpace.canPayCost`, which mirrors `effect=true` in `ComputerUtilCost.canPayCost`.

The whole scan re-runs on every priority prompt and on every mana undo, so the order of the guards in `getPossibleActions` is load-bearing, not cosmetic (#684). Keep `hasValidTargets` behind the payability guards: it calls `TargetRestrictions.getAllCandidates`, which walks every card in the target zones, and late in a Commander game most candidates are unpayable. For the same reason `canPayManaCostWithLifeFallback` returns early unless the cost actually has a shard `canPayShardWithLife` accepts — the recursion's first `canPayManaOnly` forces `AIPhyrexianPayment=Never`, which is strictly stricter than the check that already failed, so without such a shard the second probe is a foregone `false`. The stack-LKI copy behind `checkRestrictions` is memoised per host card object for one pass, so the alternative-cost variants of one face share it.

### Spells are priced on the stack, not in hand

Cost adjustment runs after `moveToStack`, so a static that only affects the stack zone — Witherbloom, the Balancer's `AffectedZone$ Stack | AddKeyword$ Affinity:Creature` — never reaches a probe on the card in hand, and `ComputerUtilMana.calculateManaCost`'s castFrom-only shim does not help (native Forge's AI has the same blind spot; its human path never predicts). `getPossibleActions` therefore enumerates in two passes: collect every ability with static checks enabled, then, when `hasStaticAbilityAffectingZone(Stack, ABILITIES)` reports such a static, run one layer pass with the stack-LKI copies as the `preList` (`applyStackStatics`, the same pre-check `GameActionUtil.getAlternativeCosts` does for its stack copy) and probe each spell with that copy swapped in as host (`canPayMana`). The final `checkStaticAbilities(false)` in the `finally` drops the copies' grants again. `ActionSpaceTest` locks the Witherbloom + Rampant Growth case on both the host and parity branches.

Action enumeration must allow Forge's static-ability checks to run. `GameActionUtil.getAlternativeCosts` evaluates hypothetical alternate hosts and stack copies under CR 601.3e; holding static checks across `getAllPossibleAbilities` suppresses granted keywords such as Hunting Velociraptor's prowl (#974). A single static pass after enumeration cannot recover the missing actions.

### Cost payment mirrors the human path on the host, the AI path in parity

`HarnessCostPlumbing.payWithControllerDecision` pays through `CostPayment.payCost` for `ManaBrewInteractiveController` (`humanCostPayment=true`) and `CostPayment.payComputerCosts` for `DeterministicController` (`false`). Only `payCost` records `paidCostParts`, and `GameActionUtil.rollbackAbility` → `CostPayment.refundPayment` refunds nothing else — so a cancelled mana payment after a `{T}` part was already paid (tap sorts before mana) untaps the permanent only on the `payCost` path. The callers in `HarnessPlayPlumbing` must hand the same `CostPayment` instance to `rollbackAbility` that paid the cost; a fresh one has an empty paid list. Parity stays on `payComputerCosts` because `payCost` asks `orderCosts` for multi-part costs, and `DeterministicController.orderCosts` shuffles with the shared agent RNG, which the Rust engine does not consume.

### Mana conversion is applied to the `CostPayment` before paying

"Mana of any type can be spent" (Tinybones, Heist, `ManaConvert` statics) lives on the `CostPayment` matrix. `payCost` hands that matrix to `payManaCost`, which puts it on the pool; a bare `CostPayment` is identity-only. `HarnessPlayPlumbing.applyManaConversion` mirrors the conversion block in `PlaySpellAbility.playAbility`, and every play path resets the pool with `restoreColorReplacements` afterwards, as Forge does. The action space cannot catch a missing conversion: `ComputerUtilMana` applies the MayPlay conversion by itself, so the spell is offered either way. `HarnessPlayPlumbingTest` locks the Tinybones case.

### Convoke / Improvise in payment

`chooseCardsForConvokeOrImprovise` declines the upfront cost reduction outside payability probes (both controllers). Convoke/improvise is then resolved at payment time: interactively in `ManaBrewInteractiveController.payManaInteractively` (`payConvoke`/`convokePaymentSources`), and automatically in `AutoPay.payConvokeImprovise` for the committing auto-pay path (only the parity runner routes through it; the host's auto button floats mana via `AutoPay.floatManaForCost` and leaves convoke/improvise taps to explicit prompt actions). Both tap the chosen creatures/artifacts, record `sa.addTappedForConvoke`, fire the `TapAll` trigger, and reduce the cost via `ManaCostBeingPaid.payManaViaConvoke`. **Parity caveat:** the Rust engine's auto-pay does not yet tap convoke/improvise sources, so `yarn parity` diverges on convoke/improvise spells until `manabrew-engine`'s auto-pay is mirrored.

### Waterbend in payment is a typed resource, not a mana ability

Convoke/improvise sources are emitted as `activateManaAbility` (`tap:<cardId>`), which leaves the client unable to tell a land tap from a cost-reduction tap. Waterbend does **not** reuse that: it emits `useResource` / `releaseResource` with `PaymentResourceKind.WATERBEND` (ids `waterbend:<cardId>` / `unwaterbend:<cardId>`), the same shape delve uses, so the UI can label and count it. Adding a `PaymentResourceKind` variant means the usual three regens — `yarn gen:types`, `yarn build:harness`, `yarn gen:protocol-docs`.

`payManaInteractively` keeps a `sessionWaterbend` shard map and a `waterbentCards` collection alongside the convoke ones. `waterbendCandidates` filters on `CardPredicates.CAN_TAP` + artifact-or-creature, mirroring `adjustCostByConvokeOrImprovise` exactly, rather than the plain `isTapped()` check `convokePaymentSources` uses. The two agree for every printed card (no card scripts an `R:Event$ Tap` replacement), so this is parity hygiene, not a live fix — but it keeps the payment surface consistent with `ActionSpace.applyWaterbendReduction`, which already uses `CAN_TAP`. `waterbendPaymentSources` offers those while `waterbentCards` is under `sa.getMaxWaterbend()` (set by then via `CostPayment` → `CostAdjustment.adjust`) and generic remains, and keeps already-waterbent cards in the list so they can be released — mirroring `delvePaymentSources`. It does not require `sa.isSpell()`: activated-ability waterbend (Watery Grasp, Katara) is the common case. An X waterbend budget (`Waterbend<X>` via RaiseCost, e.g. Crashing Wave) needs X **before targeting**, but the announce step reads the raw cost — the Waterbend<X> part only exists after `CostAdjustment.adjust` merges the static. `HarnessPlayPlumbing.announceAdjustedCostX` announces X from the adjusted cost's `getMaxWaterbend()` exactly as a scripted `Announce$ X` would (Waterbender's Restoration carries one; Crashing Wave does not — upstream native Forge is broken for this card: X resolves to 0 and targeting locks at "up to 0"). Parity note: this consumes an announce decision the Rust engine does not mirror; irrelevant while Rust lacks waterbend entirely.

`payWaterbend` pays a colorless shard via `payManaViaConvoke` — `InputSelectCardsForConvokeOrImprovise` takes the `if (artifacts)` branch for waterbend, so it never prompts for a colour even on creatures — and never calls `sa.addTappedForConvoke`, matching `adjustCostByConvokeOrImprovise`'s `creatures && !artifacts` guard; `unwaterbend` refunds the recorded shard and untaps. The auto button fills but never commits: it floats real mana via `AutoPay.floatManaForCost`, then `autoWaterbend` taps waterbend sources only for generic the pool cannot cover (guarded by `poolCanCover`, so a board is never tapped when lands suffice). The session re-prompts with the taps releasable and Confirm lit — the commit is always the player's Confirm click, and no manual tap commits either (the convoke/waterbend `isPaid` returns were removed).

### Delve in payment

Delve follows the same shape on the interactive (host) side only. `chooseCardsToDelve` declines the upfront reduction outside payability probes (returns `CardCollection.EMPTY`); the cost stays full into `payManaInteractively`, which exposes the activator's graveyard via `delvePaymentSources` (gated on the host's `DELVE` keyword and remaining generic). Picking a card (`delve` action → `payDelve`) defers it into the same `cardsToDelve` collection `CostAdjustment` would have filled — `decreaseGenericMana(1)` per card, no mid-session exile — and `undelve` reverses it (`increaseGenericMana`). The actual exile happens once, at the end, in `handleOfferingConvokeAndDelve`; cancel rolls back via the mana-payment snapshot, so there is no per-card un-exile. The host auto button greedily fills remaining generic from the graveyard (`autoDelve`) and then floats mana via `AutoPay.floatManaForCost` — it never commits; the loop re-prompts with `canConfirmFromPool` and the user confirms from the pool (`Pay` with `auto=false`). The `pay_mana_cost` prompt presents every payment option as one `PaymentAction` in a single `actions` list — mana abilities (`activateManaAbility`, id `tap:<cardId>:<idx>[:<color>]`), untap (`undoMana`, id `untap:<cardId>`), and delve resources (`useResource`/`releaseResource`). **The protocol drives; the client only renders the actions and echoes an `id` back — it holds no payment state and synthesizes no ids.** `publishManaPaymentPrompt` reads the live `cardsToDelve` set and emits each graveyard source as `useResource` (id `delve:<cardId>`) when not yet delved or `releaseResource` (id `undelve:<cardId>`) when it is, re-prompting after each toggle. The UI derives the "delved" highlight from `type === "releaseResource"` and answers `PayManaCostOutput::Act { actionId }` with the offered id (or `Pay`/`Cancel`) — never building a `delve:`/`undelve:` id itself. The distinct resource actions are earned by the separate render surface: delve lives in the graveyard zone-viewer, not the battlefield-tap surface. `ManabrewProtocolAdapter.parseActionId` decodes the id back into the internal `kind` action (`delve`/`undelve`/`tap_land`/`untap_land`). `DeterministicController` (parity) is unchanged — it still resolves delve upfront via `CostAdjustment`. The Rust engine backend does not yet offer in-payment delve, so this is host-only.

### Name-a-card prompts offer in-game names only

`ManaBrewInteractiveController.chooseCardName`/`chooseSingleCardFace` deliberately diverge from `PlayerControllerHuman`: the offered faces come from the cards in the current game (every zone plus sideboards), not `streamAllFaces()` over the catalog. This is a product decision (open-decklist semantics; keeps `StaticData` lazy loading intact and the prompt payload small), not a bug — do not "restore parity" here. The face list is filtered by the static `cpp` predicate only; the chosen name is validated once via `Card.fromPaperCard` + `isValid`, re-prompting on failure, exactly as native Forge does. Never validate per-face with `fromPaperCard` — each call burns a game card id, and doing it across the catalog tripped the runaway-game cap (the Phyrexian Revoker freeze-then-draw).

### Concede (the `Directive` channel)

Concede mirrors native Forge's out-of-band contract: `player.concede()` sets the outcome (so `hasLost()` is true immediately and `PhaseHandler` routes around the lost player), and the loss is processed by the engine's next state-based-actions pass. **Never call `checkGameOverCondition()` from inside an await** — `onPlayerLost` (CR 800.4 cleanup, reveals, lose triggers) can consult controllers, and a nested prompt published mid-await clobbers the open prompt (`latestPromptJson`) which `java_backend`'s prompt-id dedup never re-forwards: permanent deadlock. The wire carries it as a directive, never a prompt answer: `java_backend.rs` submits `{"type":"directive","directive":{"type":"concede"},"player":N}` (the seat index travels with the directive — the drain loop covers every seat, so a concede can arrive while a different player's prompt is open). `ManabrewProtocolAdapter.translateDirective` maps it to `{"kind":"concede","player":N}`, and the session's single take-core (`ManaBrewInteractiveSession.takeAction`) executes the concede **on the game thread** for the named seat. If the conceded seat is the prompted player (or the concession ended the game) the action becomes a synthetic `{"kind":"pass"}` — every await site already treats pass as its safe default — otherwise the take-core keeps waiting for the prompted player's real answer. The take-core never parks indefinitely: it polls with a 1s deadline and returns a synthetic pass once the session is closed or the game is over, so an aborted session's game thread always unwinds through the awaits' pass defaults (`close()`'s single unblocking pass is not enough on its own — the thread can re-await while unwinding). Never bypass `takeAction()` with a raw `actions.take()`.

### Restore points and the restore vote (directives, never prompts)

The node can opt into `checkpointMetrics` on its internal start request. `recordCheckpoint` records copy and bookkeeping nanoseconds only for successful checkpoints. The session owns the samples; `drainCheckpointMetrics` serializes and clears them under the same lock used to append. WASM games also enable collection: `WasmMain` supplies a session drain to `SabTransport`, which posts `forge:checkpoints` before each new prompt and at game end. `forge:decision.checkpointMs` accumulates checkpoints across bot prompts within the same human-response window. Keep checkpoint instrumentation separate from per-viewer board snapshot timing.


The session records at most one restore point (a `SessionSnapshot` pairing Forge's `GameSnapshot` with per-viewer hand knowledge) per step: at the first priority prompt a human seat gets in that step with an empty stack. Forge's snapshot restores spells on the stack but not abilities or triggers, and it does not remove stack entries created after it was taken, so every restore starts from an empty stack and `restore` clears the live stack first. The session keeps the points of the current turn and the 3 turns before it (`CHECKPOINT_TURNS`) and discards older ones when it records a new point; the kept points go out in `GameViewDto.checkpoints`, and a restore drops the points after it.

Each checkpoint owns the Forge `GameLog` lines added while it is the newest one, filtered to `GameLogVerbosity.MEDIUM` without `TURN`; `absorbGameLog` assigns them before a new checkpoint is added and before views are published, and a legacy restore clears the target's lines because its continuation is replayed. They reach clients as `CheckpointDto.log`. Journal replay rebuilds identical lines, which `JournalRewindTest` compares.

The session records the points itself, in `awaitPriorityAction`, before it publishes the prompt. Manabot seats (`botSeats`) and Forge AI seats never record, and a held pass-until or exhaust-stack pass returns before the prompt, so a fast-forward takes no points in the steps it skips. The prompt comes after the priority loop's state-based check has put waiting triggers on the stack, so a step gets its point only after they resolve; after a restore the loop runs the state-based check again. Controllers take no part in recording. The restore is applied from `ManaBrewInteractiveController.chooseSpellAbilityToPlay` through `restoreIfApproved`, because only a controller's answer can hand priority on: after `GameSnapshot.restoreGameState`, the session calls `PhaseHandler.setPriority` with the player who had priority at the point, and the controller returns an **empty list**: `PhaseHandler.mainLoopStep` treats `null` as a pass, but an empty list keeps its priority loop running, and the loop then asks `pPlayerPriority`. Returning `null` would pass priority in the restored step.

The vote is table business, not a game decision, so it never uses a prompt and never touches the prompt a player holds. `requestRestore { checkpointId }` opens a vote in `GameViewDto.restoreVote` (a new `voteId`, the checkpoint, the requester, `awaitingPlayerIds`, status `pending`); every other human seat still in the game is awaited. Forge AI seats and Manabot seats are never awaited; the start request marks Manabot seats with `players[].bot` (the browser worker from the room's bot slots, the node from the room's bot usernames). Each voter answers with `restoreVote { voteId, accept }`. One "no" ends the vote as `declined` with that player; a player who loses leaves the awaited set. `takeAction` handles both directives on the game thread. When the awaited set is empty and the open prompt is a priority prompt, `takeAction` returns the directive, `awaitPriorityAction` turns it into `PriorityActionKind.RESTORE`, and the controller restores at once; otherwise the restore happens at the next priority of a human seat. The vote ends as `approved`, or `unavailable` when the point left the ring first, and the record stays in the view until the next request.

A vote change must reach every seat without a prompt. After handling a vote directive that does not restore at once, `takeAction` raises `stateRevision` and, in the browser build, calls `InteractiveBridge.publishState`: `SabTransport` posts a `game:seat_state` event per human seat, which the host routes like a seat state frame. The node polls `getStateRevision` every loop and sends every seat its state when the revision moves; the game thread is parked in `takeAction` when the revision moves, so the snapshots do not race the game.

Recording can be switched off, and then no `GameSnapshot` is made at all. The start request carries `snapshotRecording` (default on; the browser worker fills it from the host's saved setting), so a game that starts with it off never takes one. During the game only the engine host may change it, with `setSnapshotRecording { enabled }` on the **host lane**: a lane that only the tab running the engine can write, apart from the seat lanes that carry players' directives (including those relayed from guests). The session honours it only when its `player` is `InteractiveBridge.HOST_SEAT`. Turning recording off drops the points already taken. `GameViewDto.snapshotRecording` shows every seat the current state. A node-hosted game has no client host, so recording stays as the start request set it, and the node refuses the directive from any seat.

In a browser-hosted game every seat also has a directive lane (`game:directive_lanes`, one 4096-byte `SharedArrayBuffer` per seat). `SabTransport.exchange` checks the lanes every 25 ms while it waits on the prompted seat and hands a directive to the session at once; the open prompt stays open and is not sent again (`openPrompt`/`openSeat`).

## Typed prompt emission (compile-time protocol check)

The host **does not hand-build prompt JSON.** `manabrew-protocol` (Rust) is the source of truth: `scripts/gen-harness-prompts.mjs` reads its generated TS bindings and emits one Java class per prompt input + referenced shared type into `forge-harness/src/main/java/forge/harness/protocol/` (package `forge.harness.protocol.*`), each baking in its own `type` discriminator. `scripts/harness.mjs` regenerates them before every build. The package is generated, gitignored (`forge-harness/.gitignore`), and lives under the standard `src/main/java` root on purpose: m2e/JDTLS has no build-helper connector, so an out-of-tree generated-sources dir never lands on the IDE classpath. Never hand-edit anything in this package.

`ManaBrewInteractiveSession` builds each prompt as a typed object (`new ChooseCardsInput(presentation(...), richCards(...), min, max)`) and `publishAgentPrompt(Object)` serializes it with Gson (camelCase fields, `@SerializedName` enums, nulls omitted). So a protocol change the harness no longer matches — a removed/renamed/retyped field, a dropped prompt — is a **compile error here**, not the silent runtime drift that previously killed `java_backend`'s deserialize (the `chooseType`/`chooseCardName`/`divideAmount` class of bug; `divideAmount` is now `chooseNumber`-per-target). `InteractiveSnapshotExtractor.cardDto` and state cards (`battlefield`, zone lists) are typed `CardDto` too. **Do not reintroduce raw `JsonObject` prompt building** — build the generated class. The compiler is the guard.

`publishAgentPrompt` resolves an omitted source from the currently resolving stack item. It emits `sourceAbilityText` from that stack ability, or from `castingAbility` during cast-time prompts, only when the ability host matches an explicit source. Keep this centralized fallback: Forge callbacks such as `arrangeForScry`, `arrangeForSurveil`, and `reveal` do not receive the originating `SpellAbility`, but their prompts still need the source card and ability in the envelope. Prompts outside stack resolution remain source-less unless their caller provides a source explicitly, and unmatched abilities remain absent rather than being misattributed.

Snapshots are **per-viewer**: `getSnapshot` takes a `viewer` seat index (`-1` = spectator) and `InteractiveSnapshotExtractor` gates live-card disclosure on Forge's visibility oracle — `CardView.canBeShownTo(viewer)` (including temporary hand look permissions, library hidden unless `MayLookAt`, face-down exile hidden unless the viewer may look — foretell grants the owner that right) and `canFaceDownBeShownTo`/controller for battlefield morph faces (redacted DTO, never dropped from the list, since the shell is public). Unknown hand/library cards are elided to the zone `count`; hidden exile cards stay as `{visibility:"hidden", id}` entries so clients render an anonymous face-down card. A serialized face-down card carries its real paper identity — visibility is the caller's decision, `redact()` blanks what a viewer may not see. Remembered hand cards use the frozen disclosure described below, never hidden live-card data.

Per-copy appearance is bound by `host/CardCosmeticBindings` during initial zone insertion, before identical `PaperCard` entries can lose their physical-entry association through shuffle. Clear pending entry queues at initial shuffle; later tokens must not consume deck bindings. Bindings use immutable game card IDs and retain foil plus typed cosmetics for exact owner/token-script overrides. Do not mutate shared `PaperCard` objects or recover appearance by name.

`host/CardCosmeticsCodec` validates the foundation's closed material objects before Gson conversion. Fractional material values require type-specific floating-point overrides in `scripts/gen-harness-prompts.mjs`; its generic numeric fallback is integer. `printDots.artwork` accepts booleans only, preserves false, and removes true as the inclusive default; zero amount still removes the dots object. Keep explicit zero finish coverage and rebuild both the harness and browser Web Image after cosmetic wire changes. Strict old codecs reject new fields, so these changes require the protocol owners' breaking release path.

Visible card and stack-source projections read the same bindings; hidden redaction clears foil and cosmetics. Prompt-card disclosure is explicit, not spectator visibility. Preserve bindings across checkpoints without rewinding the live card-ID counter. Rebuild the browser Web Image as well as the harness after changing this producer.

Mechanic projections use Forge's predicates and selected ability state: independent `unlockedDoors`, Case `isSolved`, exile plus `hasSuspend`, exile plus `isOnAdventure`, Prototype selection, and active `faceIndex`. Play actions use the existing `mode`; Suspend uses its `alternative`/`suspend` variant in both producers. Activated leveling uses optional `levelUp: "class" | "creature"`. Only cast choices whose emitted mode does not identify a face carry action `faceIndex`, including normal-mode MDFC spells and alternative-cost Room halves; activation and payment actions use the source card's active face. Adventure's spell half is not a transformed DFC. Visible stack entries carry the exact source/spell-LKI `sourceCard`, including its selected face, identity, foil and cosmetics. Outer identity is reserved for legitimate source-less fallbacks, never duplicated with `sourceCard`; hidden sources omit it.

Forge's LKI copier drops unlocked Room doors and the Prototype timestamp. Omit unknown LKI state rather than reporting false or locked; a spell ability's explicit `Prototype` parameter can recover its selected variant. A Room with both doors locked has an empty active name: retain its `PaperCard` name for visible printing identity without changing the live characteristics or weakening hidden-card redaction.

`CardDto.keywords` retains raw engine identifiers. Visible cards also emit `keywordLabels`, keyed by the original string and formatted with `KeywordInterface.getTitle()`. Generated rules use those labels without duplicating printed keyword lines; never expose cost DSL as rules text or parse it in the renderer. Hidden redaction clears the label map.

### Remembered opponent hands

`host/HandKnowledge` belongs to one interactive session and records only human recipients' opponent-hand disclosures. `promptCard` reuses `InteractiveSnapshotExtractor.cardDto` for zone and mechanic fields, then records the disclosure for its recipient; snapshots record current hand visibility. Retain the last-disclosed `CardDto` unchanged after publication, rather than rebuilding it from hidden live state. Forge AI, Manabot seats, spectators, and the viewer's own hand never seed this memory. It does not grant Forge look permissions or feed bot decisions. The existing visible-card entries plus the hand's total `count` carry remembered cards and anonymous backs; the session survives reconnects.

Forge reuses card IDs across zone changes: knowledge is keyed by card ID, game timestamp, and actual hand-zone owner. A public identifiable departure removes only that occurrence; an anonymous departure clears the affected owner's whole remembered hand, even when the departed card was unknown. Same-hand reordering preserves the last disclosure. New hidden draws stay unknown. `ChangeZoneEffect` conceals exiled cards **after** `GameEventCardChangeZone`, so track recent departures per viewer and handle `GameEventCardStatsChanged`; another seat's projection must not consume that viewer's pending concealment tracking.

Use the session's `captureSnapshot`/`restoreSnapshot` pair for checkpoints and mana-payment rollback. Restoring both game state and saved hand knowledge preserves earlier disclosures without retaining disclosures from the abandoned future. Unpaired Forge restore events clear knowledge.

## Boundary API discipline

`common` types are `public` only where genuinely consumed across a package boundary. `HarnessCostPlumbing` / `HarnessPlayPlumbing` / `AutoPay` expose **only** the constructor + methods the two controllers call (`payWithControllerDecision`, `isSpellPaymentContext`, `currentReservedSacrifices`, `playNoStack`, `handlePlayingSpellAbility`, `prepareSingleSa`, `orderAndPlaySimultaneousSa`, `playSaFromPlayEffect`, `payManaCost(WithTrace)`, `manaSources`, `floatManaFromSource`, `floatManaForCost`, `PayManaCostResult.paid/steps`); everything else stays package-private. When adding a member, keep it package-private unless a controller in `parity`/`host` needs it — don't widen the surface by default.

## External references (keep in sync)

- `forge.harness.Main` is the jar `mainClass` (pom) and is invoked by parity and self-hosted-node (CLI flags). Keep `Main` in the root package.
- `forge.harness.host.ManaBrewEngineAdapter` is loaded by class name in `src-tauri/src/engine_backend/java_backend.rs` (`create_instance`). Moving/renaming it means updating that string.

## Build / verify

Jar is produced by `node scripts/harness.mjs ensure` (or `mvn -pl forge-harness -am package -DskipTests` from the repository root). For a fast compile-only check against an existing fat jar:

```
javac -d /tmp/out -cp target/forge-harness-jar-with-dependencies.jar $(find src/main/java -name '*.java')
```

**After a `forge` submodule bump, do a _clean_ rebuild** (`mvn -pl forge-harness -am clean package -DskipTests`). `ensure`/`package` are incremental and key off source mtime, not the classpath — so a Forge change recompiles `forge/` but reuses the harness `.class` files compiled against the **old** Forge, silently shipping a broken jar (missing newer card enums like `CardSplitType.Prepare`, or synthetic `switch`-map classes like `SnapshotExtractor$1` → deck-load failures or a runtime `NoClassDefFoundError`). A Forge API change may also require updating the `PlayerController` overrides in `host/ManaBrewInteractiveController` + `parity/DeterministicController` (and call sites in `common/HarnessPlayPlumbing`) before it compiles. Keep the submodule pinned to the recorded gitlink with `git submodule update --init forge`; only `--remote` advances it. Build with JDK 18–21 — newer JDKs (e.g. 26) fail to compile Forge.

If a merged harness cannot find a Forge API, compare the `forge` gitlink with main before changing the harness. Git can retain a branch's rollback when main's pin is unchanged since the merge base.

## Crash reporting

`ManaBrewEngineAdapter.getGameOver` must propagate a recorded session engine error before returning a terminal-state flag. Native and JVM node bridges already convert that exception into their fatal-outcome path; returning a draw hides the failure.

Web Image's `Throwable.getStackTrace()` can return only the entry point (`WasmMain.main(:0)`). Capture `printStackTrace(PrintWriter)` for crash reporting: it retains the WASM backtrace. Keep `-H:+DebugNames` in the WASM build so those frames carry function names; `ReportExceptionStackTraces` only controls build-time diagnostics. The reported trace is capped at 8192 characters plus a truncation marker.

### Engine decision journal

Journal mode requires an isolated process, native card IDs and RNG seeding on both construction and execution threads. Name threaded engines `Game-*` so Forge's `GameAction.invoke` stays on the seeded thread. Never expose full journals or witnesses to players.

The direct `build-wasm.sh` build also needs `forge/forge-gui/res/languages` on the classpath; `FORGE_ASSETS` alone is insufficient.
