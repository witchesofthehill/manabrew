# The self-hosted node (`manabrew-rs/crates/self-hosted-node`)

Headless engine node (AI bots, automation).

The relay is the source of truth for which game a room is running: the node tags its engine session with the relay's `game_id` and aborts the session as stale whenever the relay contradicts it (room back in Lobby, or `GameStarted` for a different game); a superseded session finishing late never clears its successor's state or ends the relay's current game (the `networking-tests` crate pins this and the other disconnect/cleanup/reconnect contracts end-to-end, one Given/When/Then per test; build-checks CI runs it serialized).

Reconnects to the relay with backoff instead of exiting on socket loss, and resumes its room (`ResumeRoom` + snapshot re-broadcast from `HostSnapshot` in `host.rs`) so a relay restart doesn't kill hosted games. The bot client (`manabot::run_bot`) reconnects the same way: it retakes its seat via `JoinRoom` and pulls `RequestResync` to resume mid-game.

The published `manabrew-node` image uses Oracle GraalVM with `--gc=G1` (`GRAALVM_IMAGE`, `FORGE_GC`) and `--features graal-forge`. The node starts one child of its own executable per game (`--forge-engine-worker`), loading the native harness library there; no JVM is shipped. Approved journal rewind starts a second process, verifies the complete input prefix and target boundary, and swaps only on success. Failure keeps the original game. See `docs/DECISION_REPLAY.md`.

Hosted gameplay no longer uses the shared isolate or prewarmed JVM pool. `SELF_HOSTED_NODE_SHARED_ISOLATE` and `SELF_HOSTED_NODE_GAMES_PER_JVM` apply only to legacy benchmark paths. Each active game loads its own card database, and rewind temporarily doubles that game's engine footprint. Size `SELF_HOSTED_NODE_MAX_GAMES` and container memory for that peak. G1 supports one isolate per process, which this design preserves. Native startup validates assets; each game pays cold engine initialization.

G1 is Linux AMD64/AArch64 only; local macOS builds use Serial and cannot establish production GC behavior. `FORGE_MAX_HEAP` (default 1100m) is a per-process absolute cap and must fit the container alongside other games, rewind candidates, image heaps, native stacks and the node. Oracle Linux 10 needs `x86-64-v3`, so the amd64 image cannot be built on Apple Silicon. JVM-only `SELF_HOSTED_NODE_JAVA_*` options and `manabrew_node_jvm_*` metrics do not apply to native workers.

Each native worker samples its isolate's `forge_gc_stats` on a dedicated thread every 15 seconds and sends private telemetry on stderr. The parent sums heap gauges across live workers and adds per-worker counter deltas, including candidates; dropping a worker removes its gauges. Serial exposes collector beans (`manabrew_node_engine_gc_collections_total` and `manabrew_node_engine_gc_pause_millis_total`), while G1 does not. Collector-independent `manabrew_node_engine_stall_millis_total`, `manabrew_node_engine_stall_max_millis` and `manabrew_node_engine_long_stalls_total` measure sleep overshoot, including scheduler preemption. Their rates now sum time across independent engines, not the wall-clock fraction during which every room was stopped. A worker that stops completing decisions still reports from its sampling thread when the isolate can run.

**Decision latency is split by room shape, and the shape is the whole story.** `manabrew_node_forge_decision_seconds` is a histogram labelled `seats`, recording the rules work between a seat answering and the next prompt appearing. It carried a `bots` label until that label was found to read zero on every series it ever produced: it came from the engine's own AI seat list, which is empty for hosted games because bots join as ordinary relay clients, and only the relay knows which seats are bots. Read the histogram over a 30m window: `histogram_quantile` interpolates inside a bucket, so a quiet 5m window holding 15 decisions makes its single worst one the p99, which is how one decision between 2s and 5s once drew a 4.58s peak. Measured over two days of production captures: four seats with three bots ran a p99 near 2.9s with 2-5% of decisions over two seconds, while 2p/1bot, 2p/2bot and 4p/2bot all sat at a p99 of 0.35s with none over two seconds. It is not seat count on its own, since 4p/2bot is clean, and it is **not** bot thinking time, which is a p99 of 0.75s in exactly those rooms. A fleet-wide quantile averages the many clean rooms against the few bad ones and shows neither, which is why this label exists. The older `manabrew_node_forge_decision_stage_seconds` stays, unlabelled, as a summary: its quantiles are per process and cannot be aggregated across instances, so `max by (stage)` over the fleet was never a fleet p99. Keep it only for history from before the histogram. A decision at or above **1.5s** also logs `slow engine decision` at WARN with `game_id`, `seats`, `bots`, `elapsed_ms` and the prompt type, because the metric can say a node was slow but never which game, and finding one otherwise means replaying captures by hand.

**Logs push to Loki the same way metrics push to the gateway.** `SELF_HOSTED_NODE_LOGS_PUSH_URL` (plus `_USERNAME`, `_PASSWORD`, and `_LEVEL`, default `warn`) makes the node batch its own warnings and POST them to `loki.manabrew.app/loki/api/v1/push` every 10s. Without it the fleet's logs never leave the box it runs on: `{service="self-hosted-node"}` returned **nothing** for production and only matched `self-hosted-node-staging`, the one node that happens to run beside Loki, so the `slow engine decision` warning naming its game was written and never seen. The node pushes rather than being scraped because the fleet runs on a machine we do not install agents on, which is the same reason metrics go through a push gateway. The `instance` label is taken from the `/instance/<name>` tail of `SELF_HOSTED_NODE_METRICS_PUSH_URL` so logs and metrics carry the same node name without configuring it twice; `SELF_HOSTED_NODE_INSTANCE` overrides it. The queue holds 2048 lines and drops on overflow rather than blocking a game thread, reporting the count in the next batch, and the pusher reports its own failures to stderr only, because reporting them through `tracing` would feed the queue it is draining.

The existing parent `SIGUSR2` dump handler targets the legacy shared isolate and cannot dump isolated game workers. The native image still enables heapdump monitoring. `SIGUSR1` drains the node.

Forge deck launch preserves each card's set code, collector number, and foil finish through `CardIdentityForJava` and `ManaBrewEngineAdapter.cardRequest`. Do not reduce that boundary to name plus set: Forge can select another art in the same set, and the resulting battlefield snapshot no longer matches the deck.

Under the `java-forge` backend, `SubprocessBridge::spawn` sizes the engine JVM explicitly (`SELF_HOSTED_NODE_JAVA_HEAP_MB`, default 1024; `SELF_HOSTED_NODE_JAVA_ACTIVE_PROCESSORS`, default 2; either set to `0` to fall back to JVM ergonomics; `SELF_HOSTED_NODE_JAVA_GC_LOG` = `stderr` or a directory, for `-Xlog:gc*`; `SELF_HOSTED_NODE_JAVA_OPTS` appended last) — a fleet runs dozens of these side by side and every JVM would otherwise size its heap and GC thread count from the whole machine (#684). `-XX:+ExitOnOutOfMemoryError` is always set; the endstep concurrency patches assume it. Prefer `stderr` in a container: alloy ships container output to Loki and nothing ships files, and the subprocess owns stdout for the protocol. GC lines are forwarded at `info` (the rest of the engine's stderr stays at `debug`). When setting `SELF_HOSTED_NODE_JAVA_HEAP_MB`, raise the container's `mem_limit` with it — the heap cap does nothing if the cgroup kills the process first, and the JVM's non-heap plus the node itself need roughly another 500MB.

A background `updater` monitor (`updater.rs`) polls the version manifest (default `play.manabrew.app/manifest.json`) and compares its own `CARGO_PKG_VERSION` against `packages["self-hosted-node"]`; when behind it logs a warning, or — with `--shutdown-on-stale` / `SELF_HOSTED_NODE_SHUTDOWN_ON_STALE` — gracefully cancels its rooms (relay sockets get a proper WebSocket close) and `exit(0)`s once idle (no `engine_session` active in any room) so a pull-on-restart supervisor respawns it updated. SIGTERM/SIGINT trigger the same graceful room shutdown. Do not enable the flag under plain `restart: unless-stopped` (re-runs the same image → crash loop); it needs a supervisor that pulls latest on restart.

## The direct data plane

A headless node offers no plane; its rooms stay on the relay. Under `forge-room` a desktop host
installs a `ShellBridge` that serves WebRTC seats through the webview. See `docs/TRANSPORT.md`.

## Game outcome

The relay no longer reads how a game ended off the state stream (`docs/agents/RELAY.md`, `ReportGameOutcome`); the node files it. `spawn_game_over_forwarder` builds the report from the final `State` in the game-over batch, or, when the backend sends none (the Rust engine), from the last state the node cached in `HostSnapshot`, and only if that one says the game is over. It goes out after the final envelopes and before `EndGame`, so the relay still holds the replay cache when it lands. An engine panic or error files `fatal_message` instead, ahead of the `Fatal` envelope.

Hosted Forge sessions enable journal history for external decision makers and do not create `GameSnapshot` restore points. Their snapshot-copy metrics therefore remain zero. Legacy sessions opt into `checkpointMetrics` in the internal start request. The Java session times successful restore-point creation with `System.nanoTime()`: `copy` covers `GameSnapshot` construction and `makeCopy`; `bookkeeping` covers retention/eviction and checkpoint-view rebuilding. Samples are drained per session through `drainCheckpointMetrics` (JVM command or `forge_drain_checkpoint_metrics` in Graal) once per new prompt and at normal game end. Polling the same prompt does not count samples twice. Browser sessions drain the same timers through `SabTransport` into their per-game engine report; benchmarks leave collection disabled.

`manabrew_node_forge_checkpoint_seconds{stage,seats}` is a histogram with `copy`, `bookkeeping`, and `total` stages, in seconds. Each stage has one observation per successful checkpoint; use `stage="total"` for checkpoint counts and total cost, rather than summing stages. `manabrew_node_forge_checkpoint_decision_seconds{seats}` records the accumulated checkpoint time for each measured decision, including zero-cost decisions. Startup and terminal checkpoint samples enter the creation histogram only. A killed or aborted session can lose unreported samples. Decision elapsed time is sampled before draining telemetry so that the metrics round trip does not inflate that observation. The Live Ops dashboard charts means, p95/p99, time per decision and its fraction of decision time. These timers measure synchronous wall time, including pauses during copying, but cannot attribute later GC to retained checkpoints.
